## 范围与结论

用户反馈已通读第一至六章，并主动要求场景问答。本轮围绕下单串联职责、事务、并发、幂等、缓存、文件存储、测试与部署路径；是抽样检查，没有覆盖全部小节，也没有执行代码或真实环境验证。

初步判断：能提出主要处理方向，部分重要边界能自行说明；把方向变成并发下可靠、可验证的执行方案时，细节仍需练习。区分独立回答与讲解后复述，不用提示后的正确回答直接证明已经独立掌握，也不根据本次问答给出精确分数。

## 本轮澄清的关键区别

- 真实条件 UPDATE 的影响行数是数据库执行结果；Mock 固定返回 1 是测试预设结果，不能证明 SQL 正确。
- Mock 可以替换 Mapper、Redis 或外部客户端，帮助验证成功与异常分支；是否发送 HTTP、是否连接真实数据库，要看测试具体配置，不由“测试”二字自动决定。
- 事务回滚验证需要在业务事务结束后检查真实数据。模拟抛异常、打印回滚日志与证明数据库已回滚不是同一件事。
- 先查询不存在再插入仍有并发窗口；普通订单自增主键不能代替下单操作标识的唯一约束。
- 删除缓存成功、删除失败后可靠重试与 TTL 兜底分别处理不同问题。内存中的重试任务可能随应用重启丢失。
- 两次真实购买可以分别创建订单；是否提醒已有订单由业务决定。真正的限购或禁止重复购买必须由后端保障。

## 把“查数据库记录”变成明确断言

本轮最后案例：初始库存 5，通过对外入口购买 2 件，接口返回 200 和订单 ID。用户回答会核查数据库记录，以下为讲解补充，尚未让用户独立列全：

- 在约定无其他并发改动的测试中，库存应为 3。
- 对应订单及明细确实存在，关联到本次返回的订单 ID，买家、商品与购买数量正确。
- 成交单价、优惠及最终金额符合后端规则；订单状态与本次操作一致。
- 测试在预期环境与版本执行，必要的后续任务或副作用状态符合该业务约定。

这些是不同层次的证据；不能用订单 ID 非空或一条成功日志替代业务结果检查。
