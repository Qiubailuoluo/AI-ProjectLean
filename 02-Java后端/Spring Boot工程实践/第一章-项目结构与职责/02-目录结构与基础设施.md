# 目录结构与基础设施

所属章节：[[00-第一章-项目结构与职责]]。按章节导读的顺序阅读，也可以作为复习专题。

## 按什么方式组织目录

### 按技术层

```text
controller/OrderController.java
controller/ProductController.java

service/OrderService.java
service/ProductService.java

mapper/OrderMapper.java
mapper/ProductMapper.java
```

直观，适合简单项目，但修改一个业务需要跨目录查找，业务增长后单个目录容易膨胀。

### 按业务模块，再在内部按层组织

```text
order/controller/OrderController.java
order/service/OrderService.java
order/mapper/OrderMapper.java

product/controller/ProductController.java
product/service/ProductService.java
product/mapper/ProductMapper.java
```

当前学习优先采用第二种：同一业务代码集中，便于围绕需求理解和检查 AI 修改。

**业务包不等于 Maven 模块，也不等于微服务。** 多个业务包可以位于同一个 Spring Boot 应用、同一个 pom.xml 下，一起构建和部署。
## 完整目录示例

假设采用 MyBatis，部分 SQL 写在 XML 中。目录并非必须填满的清单。

```text
shop/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/com/example/shop/
    │   │   ├── ShopApplication.java
    │   │   ├── order/
    │   │   │   ├── controller/OrderController.java
    │   │   │   ├── service/OrderService.java
    │   │   │   ├── mapper/OrderMapper.java
    │   │   │   ├── entity/OrderEntity.java
    │   │   │   └── dto/
    │   │   │       ├── CreateOrderRequest.java
    │   │   │       └── OrderResponse.java
    │   │   ├── product/
    │   │   │   ├── service/ProductService.java
    │   │   │   ├── mapper/ProductMapper.java
    │   │   │   ├── entity/ProductEntity.java
    │   │   │   └── dto/ProductPurchaseInfo.java
    │   │   ├── user/
    │   │   ├── config/
    │   │   ├── infrastructure/storage/
    │   │   └── common/
    │   │       ├── exception/
    │   │       └── response/ApiResponse.java
    │   └── resources/
    │       ├── application.yml
    │       └── mapper/OrderMapper.xml
    └── test/java/com/example/shop/
```

java 放源码；resources 放配置和运行时资源；test 放测试。Mapper 接口和 XML 位置不同，但共同承担数据访问职责。启动类位于根包，业务包通常位于其子包；具体组件与 Mapper 扫描配置仍需正确设置。
## 公共代码与基础设施

- 谁能上传商品图片、图片归属哪个商品：商品业务。
- 调用 MinIO 上传并返回结果：文件存储组件。
- Redis 连接配置：技术配置。
- 缓存什么、什么时候失效：结合对应业务决定。
- 全局异常处理、统一响应结构：可以放公共位置。

**技术组件提供能力，业务模块决定如何使用。** 不要因为两处用到某段业务规则，就放进 common；也不必把全部 Redis 行为塞进巨大的 RedisUtils。
