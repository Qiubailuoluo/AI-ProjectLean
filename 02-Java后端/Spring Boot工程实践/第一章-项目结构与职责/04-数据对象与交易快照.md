# 数据对象与交易快照

所属章节：[[00-第一章-项目结构与职责]]。按章节导读的顺序阅读，也可以作为复习专题。

## 模块数据契约与交易快照

商品模块不必返回完整 Entity，可以返回购买所需信息：

```java
public record ProductPurchaseInfo(
    Long productId,
    String productName,
    BigDecimal salePrice
) {}
```

Record 只是示例，旧版 Java 可用普通类。契约由商品模块提供，订单不必依赖成本价、供应商、内部备注等存储细节。

| 数据 | 负责方 |
| --- | --- |
| 商品当前名称、售价、可售状态 | 商品模块 |
| 本次订单最终成交金额 | 订单业务，结合价格与优惠规则确定 |
| 下单时名称、成交单价、数量 | 订单模块保存快照 |

历史订单不能每次读取商品当前价格作为成交价格。商品改名、改价后，历史交易事实仍应保留。

价格是否允许在提交期间变化、何时重新确认，需要额外业务约定；DTO 本身无法保证。
## DTO、VO、PO 与统一响应

缩写存在项目差异，先看项目约定。

| 名称 | 常见含义 |
| --- | --- |
| DTO | 数据传输对象，可以是入参、出参或模块交互对象 |
| VO | 有些项目指展示对象；领域设计中也可能指值对象 |
| PO / Entity | 持久化对象，常对应数据库记录 |

当前优先明确命名：CreateOrderRequest、CreateOrderCommand、OrderResponse、ProductPurchaseInfo、OrderEntity。Request 表达 HTTP 请求，Command 表达业务动作的输入；两者是否拆分及字段改名示例见 [[03-Service组织与模块协作]] 的“Request 与 Command”一节。

请求结构限制调用方能提交什么；Entity 表达存储；响应结构决定能公开什么。前端提交商品 ID 和数量，成交金额由后端决定，不应因直接接收 Entity 而允许客户端任意指定。

统一响应是外壳，响应 DTO 是其中的业务数据：

```text
ApiResponse<OrderResponse>
├── code
├── message
└── data: OrderResponse
```

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {"orderId": 10001, "amount": 299.00, "status": "CREATED"}
}
```

统一响应不等于全部 HTTP 状态都使用 200。下载、流式响应等也可能采用其他形式，接口章节再深入。

字段相似不代表职责相同，但简单接口也不必逐层建立大量相同对象。按实际边界与差异决定拆分和转换。
