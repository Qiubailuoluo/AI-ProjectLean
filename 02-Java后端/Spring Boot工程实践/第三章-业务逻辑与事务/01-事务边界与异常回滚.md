# 事务边界与异常回滚

所属章节：[[00-第三章-业务逻辑与事务]]。

## 共同生效的数据库操作

下单先扣库存、后保存订单。如果保存失败，库存不应无故减少。
可将两项操作纳入同一次数据库事务，按规则共同提交或回滚。

跨 Service、跨业务包不自动切断事务。这里讨论同线程、同一事务管理范围、正确接入 Spring 的数据库访问；已有事务时，默认 REQUIRED 传播通常加入它，不是每个注解都创建独立事务。

MySQL 本地事务不会自动撤销 Redis 修改、MinIO 上传、远程调用、已发送短信。已提交的独立事务也不能靠后续本地回滚自动撤销。

## 异常与回滚

默认未定制回滚规则时，RuntimeException 和 Error 触发回滚，受检异常默认不触发；可以按需配置 rollbackFor，项目也可能修改默认规则。

```text
业务方法抛出符合规则的异常
  → 异常离开事务方法
  → 事务代理处理回滚
  → 异常继续传播
  → MVC 统一异常处理生成 HTTP 响应
```

发现业务不允许时直接抛异常，不必为了执行步骤先写 try。若检查失败前未发生写入，就没有库存等变更需要撤销。

```java
@Transactional
public void createOrder() {
    deductStock();
    try {
        saveOrder();
    } catch (RuntimeException e) {
        // 错误示意：吞掉失败，正常返回
        return;
    }
}
```

此时若没有其他机制标记事务为 rollback-only，就可能提交前面的扣减。但不能记成 catch 一定提交：内部事务调用或底层异常可能已标记只能回滚，最终提交仍可能失败。

## 没手写 throw，为什么也会抛异常

数据库驱动、MyBatis、Spring 等内部代码会发现连接或执行故障并抛出、包装或转换异常。应用方法即使未写 throw，也可以向外传播这些异常。

| 写法 | 含义 |
| --- | --- |
| throw | 实际抛出异常 |
| throws | 声明可能向外抛出的异常 |
| try/catch | 捕获异常并处理 |

非受检异常无需在方法签名声明 throws。

查询不到商品通常返回 null；更新无匹配记录通常返回零行，这些不必然抛异常，需要业务代码判断后表达失败。

连接中断、提交阶段故障可能使应用无法立即确认最终结果。不能将失败响应一概理解为已经确定回滚成功，更不能据此盲目重试。
