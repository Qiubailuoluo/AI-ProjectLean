# 库存并发与请求幂等

所属章节：[[00-第三章-业务逻辑与事务]]。

## 事务不自动防止超卖

库存剩一件，两笔事务可能同时普通查询得到 1，并都通过 Java 判断；若随后无条件减一，就可能减到负数。各事务都正常提交并不意味着业务规则正确。

将库存条件放进更新，检查影响行数（MyBatis 占位示意）：

```sql
UPDATE product
SET stock = stock - #{quantity}
WHERE id = #{productId}
  AND stock >= #{quantity};
```

前提是 quantity 已校验为正数，id 为唯一标识，采用 InnoDB。更新与锁机制协调同条库存记录的竞争。

```java
int rows = productMapper.deductStock(productId, quantity);
if (rows != 1) {
    throw new BusinessException("库存不足或商品不可用");
}
```

零行还可能代表商品不存在，不应仅凭它精确断言库存不足。条件更新防止本扣减路径扣成负数，事务确保后续保存失败时一起撤销。所有修改库存的入口都需要遵守正确规则。

## 为什么需要幂等

订单提交成功但响应丢失，客户端超时后重试，可能再次创建订单。客户端超时不表示后端没成功。

同一购买意图的重试沿用同一请求标识；新购买使用新标识。标识应包含用户、操作等作用域，同标识不同请求内容需要检测并拒绝冲突。

| 机制 | 解决的问题 |
| --- | --- |
| 事务 | 多个操作共同提交或回滚 |
| 库存并发控制 | 不错误扣减库存 |
| 幂等控制 | 同一次意图不重复生效 |

## 数据库方案

可记录用户 ID 与请求标识并设置唯一约束，订单和库存纳入同一事务。两个请求同时到达时，不能只靠 exists 查询，唯一约束负责阻止重复落单。

重复时查询已有结果；只有确认违反对应幂等约束才能当作重复请求，不能吞掉所有数据库错误。事务失败后的重复结果读取应安排在合适的事务边界之外，避免在已失败事务里继续操作。

## Redis 方案及边界

原子占位示意，60 秒并非固定推荐值：

```redis
SET idem:create-order:用户ID:请求标识 处理者标识 NX EX 60
```

设置成功获得资格，失败则检查 PROCESSING 或 SUCCESS 状态。成功记录订单 ID 或结果，处理中按约定返回或等待。

风险窗口：数据库已提交 → 应用退出 → Redis 成功状态未写入 → 标识到期 → 重试再次执行。业务超过占位有效期、key 丢失或被淘汰也可能产生重复。

因此 Redis 原子占位不等于完整业务幂等。重要订单可由 Redis 快速拦截、持久化唯一标识保障最终不重复。幂等记录保留多久也决定允许重试的时间窗口，需显式约定。

更新或删除占位时应原子校验处理者身份，避免旧请求误删新请求记录。不能一律在 finally 中直接 DEL；成功去重结果与短期执行锁也不是同一种生命周期。
