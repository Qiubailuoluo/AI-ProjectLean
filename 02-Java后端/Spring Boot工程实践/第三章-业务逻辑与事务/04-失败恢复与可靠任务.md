# 失败恢复与可靠任务

所属章节：[[00-第三章-业务逻辑与事务]]。

## 回滚、重试、补偿

| 方式 | 含义 | 例子 |
| --- | --- | --- |
| 回滚 | 撤销当前未提交事务内的修改 | 保存失败，库存扣减撤销 |
| 重试 | 再次执行操作 | 通知短暂超时，之后再发送 |
| 补偿 | 用新业务动作修正已生效结果 | 取消已提交订单并返还库存 |

网络故障可能适合重试，但参数错误、已下架等不该原样无限重试。请求超时也可能已经成功，应结合幂等和结果查询处理。

取消不是把过去的创建事务倒放，而是新的状态转换。重复或并发取消不能多次返库存，状态条件更新、事务和幂等仍需要配合。

短信失败通常不意味着必须取消订单；是否补偿由业务要求决定。

## 外部通知如何可靠执行

```text
同一个数据库事务：
  扣库存 + 保存订单 + 保存待通知记录
                ↓ 提交
后台读取任务 → 发送 → 记录成功
                ↓ 失败
            按规则重试
```

这是本地消息表 / Outbox 思路。事务保证订单与需要发送的任务一起保存，不保证远程发送本身与数据库原子完成。

发送成功、更新任务状态前进程退出，可能再次发送，因此接收方仍需按稳定事件 ID 去重。重试需要次数、退避、监控和人工处理等策略，尚未展开具体实现。

## 提交后事件不等于可靠消息

Spring 的 @TransactionalEventListener 可绑定事务阶段，默认 AFTER_COMMIT。它不自动提供持久化、跨进程可靠投递，也不表示自动异步。无事务时默认不执行，除非显式配置回退行为。

不要用一个内存事件替代必须可靠完成的任务记录。提交后处理失败时，原事务已提交，不能因此假装核心业务未发生。

## 当前学习约定

- 简单数据库业务：Service 业务入口事务，内部步骤共同参与。
- 存在慢外部调用：划分编排与短事务，确认结果有效性。
- 外部操作必须最终完成：考虑持久化任务、重试、幂等。
- 已生效的跨步骤业务需要恢复：明确补偿，而非依赖本地回滚。
