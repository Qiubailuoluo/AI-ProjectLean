# 命名与代码可读性

所属章节：[[00-第五章-工程规范与质量]]。回看：[[01-分层职责与校验]]、[[03-Service组织与模块协作]]、[[04-数据对象与交易快照]]。

## 1. 名称首先说明业务含义

假设 AI 新增了 `handleData()`，只看调用处很难知道它在检查商品、计算金额，还是已经创建订单。名称应该让调用者预期输入、结果和副作用，再通过类型与正文确认细节。

| 含义模糊的示例 | 可以考虑的名称 | 仍要核对什么 |
| --- | --- | --- |
| `handleData` | `createOrder` | 是否真的负责创建订单，而非任意修改数据 |
| `checkStock` 返回 boolean | `hasEnoughStock` | 只是当次判断，不承诺并发下已预留库存 |
| `checkStock` 失败时抛异常 | `requireEnoughStock` | 明确说明失败语义，且不能代替可靠扣减 |
| `update` | `cancelOrder` | 是否包含订单状态、权限和恢复动作 |
| `time` | `createdAt`、`paidAt`、`expiresAt` | 时间含义、时区与单位是否一致 |
| `count` | `requestedQuantity`、`affectedRows` | 是用户购买数量还是 SQL 更新结果 |

这些名称是表达思路的例子，不是必须采用的固定词汇。尤其不能只把 `checkStock` 改个名字，就宣称超卖问题已经解决，相关保障见 [[03-库存并发与请求幂等]]。

## 2. 风格统一，但不要把风格当作正确性

Java 项目常采用类名 `UpperCamelCase`、方法和变量 `lowerCamelCase`、包名小写；常量通常使用 `UPPER_SNAKE_CASE`。这里的常量不只是“声明为 final 的所有变量”，可变对象的引用不变也不代表其内容不可变。

同一项目沿用已有风格，减少阅读负担。Google Java Style 可作为一套完整参考，但不是 Spring Boot 的强制规则；代码不满足某个风格偏好，也不直接说明业务错误。[Google Java Style](https://google.github.io/styleguide/javaguide.html)

避免无解释缩写、混用同义术语和单位缺失。比如同一业务概念不要一处叫 `buyerId`、另一处叫 `customerId`，却没有说明是否对应同一身份。若团队已有明确术语，优先遵循，而非擅自全库改名。

## 3. 对象名称说明跨越哪条边界

沿用第一章约定：

```text
CreateOrderRequest   客户端允许提交的字段
OrderResponse        对外展示的订单结果
OrderEntity          数据库持久化结构
ProductPurchaseInfo  商品模块提供给购买流程的数据契约
```

不同对象即使暂时字段相似，也可能具有不同变化原因。反过来，简单单入口场景也不必机械地增加 `Request → Command → DTO → Result → VO` 五层转换。先明确职责和变化需求，再选择对象边界。

名称不能替代实际约束：叫作 `OrderResponse`，也仍要检查是否暴露内部成本或其他用户信息；叫作 `CreateOrderRequest`，也不能默认允许客户端指定成交金额和买家身份。

## 4. 方法表达连贯流程，细节按需要拆分

下面是职责示意，不是完整可运行代码：

```java
public OrderResponse createOrder(Long userId, CreateOrderRequest request) {
    ProductPurchaseInfo product = loadPurchasableProduct(request.getProductId());
    BigDecimal amount = calculateOrderAmount(product, request.getQuantity());
    deductStockReliably(product.getId(), request.getQuantity());
    OrderEntity order = saveOrder(userId, product, request.getQuantity(), amount);
    return toOrderResponse(order);
}
```

主流程能让读者看到“取商品、算金额、扣库存、存订单、组织结果”。是否需要事务、如何可靠扣减、查询商品与并发修改如何协调，需要遵守第三章的真实方案，不能从这段示意的名称推断已经保障正确。

考虑拆方法的理由包括：一段逻辑有独立含义、分支需要单独理解、规则被复用，或细节遮住主流程。不要因为“每个方法不得超过十行”就制造大量没有含义的转发方法，也不要仅为形式给每个 Service 配一份空接口。

同类内调用的事务代理边界不会随着拆分自动改变，见 [[02-事务代理与业务流程组织]]。

## 5. 避免嵌套过深，但保留失败含义

可以先处理不合法情况，再展开正常流程，减少多层 `if`。例如数量不合法、商品不存在、商品已下架，分别返回明确失败，而不是都变成 `null` 或“操作失败”。

提早返回与抛出业务异常都是表达方式，需要结合方法契约选择。不能为了压平嵌套吞掉异常、忽略影响行数，或者让调用方无法判断“本来不存在”和“数据库故障”。统一异常响应见 [[00-第二章-接口设计与数据流转]]。

## 6. 常量、枚举与注释各解决什么

| 做法 | 适合解决的问题 | 常见误用 |
| --- | --- | --- |
| 有含义的常量 | 重复且含义稳定的参数，如本例分页大小上限 | 给只用一次的普通数字强行起很长的名字 |
| 枚举或明确的状态模型 | 有限的订单状态与合法取值 | 假设只要用了枚举，就自动约束所有状态转换 |
| 配置项 | 需要随环境或运行要求调整的参数 | 把商品售价、用户权限等业务数据塞进配置文件 |
| 注释 | 为什么保留某个限制、单位、外部协议和兼容原因 | 逐句翻译代码，或说明与实现已经不一致 |

订单从 `CREATED` 到 `CANCELLED` 是否允许，需要业务检查；枚举只表达状态取值本身。对外或持久化的枚举值还要考虑兼容，不能随意按显示顺序保存序号后又调整顺序。

好的注释可以说明：“这里保存成交时商品名称，避免订单历史随商品改名变化。”不必仅写“设置商品名称”。TODO 应说明缺口和影响，不能让读者误以为关键失败处理已经实现。

## 7. 怎样审查一次 AI 可读性修改

先看修改是否服务于当前需求，再看名称和行为是否一致。重命名要同步调用点、配置或映射中的引用以及必要文档；不能只改一个 Java 方法名就认定所有引用已修复。

所谓“不改变行为的重构”，也需要现有测试、关键场景或差异检查作证据。重命名不应顺便改变订单状态码、事务边界、排序规则或异常含义；若确实需要改变，应单独说明原因和验证。

当前尚未对真实项目重构。阅读后可选择一段已有 Service 主流程，先描述它做什么，再核对命名是否一致，而不是一开始批量重写所有文件。
