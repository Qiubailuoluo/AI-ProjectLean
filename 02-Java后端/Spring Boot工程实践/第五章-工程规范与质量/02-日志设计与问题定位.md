# 日志设计与问题定位

所属章节：[[00-第五章-工程规范与质量]]。回看：[[00-第二章-接口设计与数据流转]]、[[05-慢查询定位与优化验证]]。

## 1. 日志要帮助重建一次事情的经过

用户说“刚才下单失败了”。只有“执行失败”四个字，不能判断是输入错误、库存不足、数据库异常，还是请求其实已完成但响应丢失。

围绕订单流程，可以记录请求关联标识、操作名称、必要的业务标识、结果和耗时；系统异常还要保留异常类型与调用栈。目的不是把全部变量倒出来，而是留下能缩小问题范围的证据。

| 字段 | 本例含义 | 使用边界 |
| --- | --- | --- |
| 时间、应用实例 | 在什么时刻、哪个运行实例观察到事件 | 多实例日志需有统一时间和时区约定 |
| requestId / traceId | 关联同一次请求或跨服务调用链 | 单次请求 ID 不自动等于完整分布式追踪 |
| operation | 如 `createOrder`、`invalidateProductCache` | 名称稳定，便于检索 |
| orderId / productId | 定位对应业务对象 | 按项目数据规范控制范围，不记录无关个人信息 |
| result / errorCode | 成功、预期业务失败、系统故障 | 中文提示文案不能代替稳定结果分类 |
| costMs | 这一步或整次操作耗时 | 明确计时范围与单位，不混淆数据库耗时和请求总耗时 |

## 2. 应用怎样输出日志

常见 Spring Boot 应用使用日志门面来写日志，由具体实现负责输出、级别与格式。应用层可以使用 SLF4J；常见 starter 组合默认带有 Logback，不必为打印一行日志再引入多套日志实现。实际以依赖树为准。[Spring Boot 日志说明](https://docs.spring.io/spring-boot/reference/features/logging.html)

下面是假设已经获得 `log` 和关联上下文的代码片段，非完整可运行代码：

```java
log.info("Order request received requestId={} productId={}",
        requestId, productId);

log.error("Order persistence failed requestId={} productId={}",
        requestId, productId, exception);
```

占位符让模板与值分开，异常对象按相应 API 的约定作为参数传入，才能保留调用栈。只记录 `exception.getMessage()` 往往丢失错误位置，不能把它当作完整异常日志。[SLF4J Logger 接口](https://github.com/qos-ch/slf4j/blob/master/slf4j-api/src/main/java/org/slf4j/Logger.java)

占位符不是万能的性能优化：`log.debug("data={}", expensiveCalculation())` 中的方法仍可能先执行。确实存在昂贵参数构造时，再考虑级别判断或所用版本支持的延迟求值能力；不是每行日志都需要额外包一层判断。

`System.out.println` 可以用于临时观察，但缺少统一的级别、格式和上下文约定，不作为应用长期排查方式的起点。

## 3. INFO、WARN、ERROR 怎样选择

以下是本例建议，不是所有团队必须相同的规则：

| 级别 | 倾向用途 | 订单案例 |
| --- | --- | --- |
| DEBUG | 开发或针对性排查细节 | 某条分支选择、脱敏后的关键参数 |
| INFO | 有价值的正常事件 | 关键业务结果、应用启动与配置摘要 |
| WARN | 异常趋势或可恢复问题，需要关注 | 缓存失效失败进入重试、外部服务反复超时 |
| ERROR | 本次操作或后台任务的严重故障，需要处理 | 数据库写入异常、关键任务持续失败 |

用户数量填错、商品自然下架、正常库存不足，不必全部用 ERROR 打满调用栈。是否记录及其级别要结合业务频率与排查价值。相反，不能为了“日志好看”把真正的数据库故障降为 DEBUG。

选择一处承担完整异常记录责任。例如底层补充必要上下文，统一处理边界记录调用栈并组织响应；不要每层都捕获、ERROR、再抛出，造成同一次失败出现五份相同堆栈。可以记录不同语义的事件，但要能区分。

## 4. 记录的时间点必须与事实一致

`saveOrder()` 返回不代表整个事务一定已经提交；方法末尾打印“订单创建成功”，也可能先于事务代理最终提交。提交阶段仍可能失败，事务机制见 [[01-事务边界与异常回滚]]。

区分“开始处理”“订单已生成待提交”“业务提交已确认”“外部结果不确定”等事实。确需提交后事件时，按事务机制安排执行，不以日志所在的代码行数判断提交时机。缓存删除失败进入重试，也不等于已经提交的订单自动失败。

日志记录失败通常不应改变普通业务结果；需要可靠、可审计的业务事实时，应设计相应持久化与交付机制，而不是依赖一次普通日志输出。日志不是订单数据库，也不是可靠任务队列。

## 5. 让关联信息贯穿调用链

在入口建立可信的关联标识，并贯穿 Controller、Service、数据库访问与必要的外部调用。有些日志系统可通过 MDC 将标识放入每条日志的上下文，但上下文的建立、传递与清理仍需正确处理。

线程池、异步任务和跨服务调用不一定自动携带当前上下文；线程复用时也不能把上一请求的信息留给下一请求。不能只看到日志模板里有 `traceId` 字段，就认定追踪已经接通。具体实现放后续实践，不在本篇引入一整套监控平台。

## 6. 不把请求与响应原样记录下来

订单排查通常只需要少量业务标识和错误分类。密码、令牌、Cookie、数据库连接凭据、私有文件签名 URL，以及无关个人信息不应被顺手写入日志。必要参数按数据规范脱敏、限长，文件内容也不整段输出。

打印真实 SQL 与参数可能帮助定位慢查询，但同样需要范围控制。不要在生产环境无限量记录所有查询、全部请求体，再用“有日志”代替定位能力。故障排查时临时提高级别，需要明确范围和恢复方式。

## 7. 配置、指标和日志配合

日志级别示意，具体包名按真实项目替换：

```yaml
logging:
  level:
    root: INFO
    com.example.shop.order: DEBUG
```

这表示可以对订单包单独提高详细程度，而非全应用都打开 DEBUG。日志输出到控制台还是文件、如何收集、轮转和保留，要结合运行方式安排，留到第六章深入。

“最近十分钟错误率升高”更适合先看指标；“这一次失败经过哪些步骤”更适合看关联日志；“跨多个服务哪里耗时”可能需要调用链追踪。三者配合，不能把日志越多等同于可观测性越好。

## 8. 一次排查怎样形成闭环

从时间范围、请求标识和操作结果定位日志；确认异常发生在输入、业务、数据库还是外部服务；结合数据库记录、执行计划或任务状态核实实际结果。连接中断时，不能仅凭一条 ERROR 就认定业务一定回滚。

修改后用相同场景核对结果、关联信息与耗时，检查日志是否足以定位、是否重复及是否含不该出现的数据。当前只提供学习方案，没有检查真实日志，也未进行性能或故障实验。
