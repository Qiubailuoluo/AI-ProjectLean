# 配置管理与环境隔离

所属章节：[[00-第五章-工程规范与质量]]。回看：[[02-目录结构与基础设施]]、[[07-Redis缓存读写与一致性]]、[[08-MinIO文件与业务记录管理]]。

## 1. 哪些信息应该进入配置

同一份应用代码在本机、测试和生产运行时，数据库位置、文件存储地址、超时等参数可能不同。把这些差异从业务代码中分离，便于替换和管理；不是把所有会变化的信息都塞进 YAML。

| 信息 | 本例归属 | 为什么 |
| --- | --- | --- |
| 数据库地址、缓存连接参数、MinIO 入口 | 环境配置 | 与部署位置和运行资源有关 |
| 外部调用超时、缓存有效期、分页上限 | 可配置参数或明确的项目默认值 | 需要结合容量与业务容忍度调整 |
| 密码、访问密钥、令牌 | 受保护的凭据来源 | 需要控制分发、使用和更新 |
| 商品售价、用户收货信息 | 业务数据 | 需要业务读写、校验与相应持久化 |
| 订单允许怎样转换状态 | 业务规则 | 不能靠随意改配置绕开状态约束 |

某些业务确实需要可配置规则，但应单独设计权限、版本、生效和校验流程，不能用一个 `application.yml` 代替业务管理系统。

## 2. Spring Boot 从哪里读取配置

Spring Boot 可读取 properties、YAML、环境变量、命令行参数等来源，并按优先级组合结果。不能只看仓库里的一个文件，就确定应用当前采用什么值。[Spring Boot 外部化配置](https://docs.spring.io/spring-boot/reference/features/external-config.html)

常见排查场景是：仓库里端口为 8080，运行时却是另一端口，因为启动参数或外部环境覆盖了它。需要核对启动方式、外部文件、激活的 Profile 与最终有效配置，而不是反复修改代码内的默认值。

不要背一条过度简化的“所有配置永远按 A 大于 B”规则。测试专用属性、外部配置位置、同目录的格式差异等也会影响结果，实际优先级应查看所用版本文档。修改文件或环境变量也不保证正在运行的应用自动刷新，需按项目的加载和生效机制操作。

## 3. Profile 分组不等于环境已经隔离

```text
application.yml        通用且合理的默认配置
application-dev.yml    本地开发差异
application-test.yml   自动测试差异
application-prod.yml   生产差异或所需参数说明
```

命名是常见示例。通过 `spring.profiles.active` 选择激活的 Profile，可从环境变量或启动参数等来源提供。不要把 `spring.profiles.active` 写进 `application-prod.yml`，再期望该文件靠自己激活自己；Profile 专用文件有相应约束。[Spring Boot Profiles](https://docs.spring.io/spring-boot/reference/features/profiles.html)

Profile 只是配置选择机制。若 `test` 和 `prod` 仍连接同一个数据库、同一个私有附件 Bucket，并使用有写权限的同一账号，写了两个文件也不代表测试已经隔离。

| 资源 | 需要核对的隔离点 |
| --- | --- |
| MySQL | 独立测试库或实例、账号范围、初始化和清理机制 |
| Redis | 独立实例或明确的 Key 空间和权限；逻辑 DB 号不是完整安全隔离 |
| MinIO | 测试 Bucket/前缀及受限凭据，清理不能触及生产文件 |
| 外部服务 | 测试接口或替身，避免测试真的发短信、扣款或触发其他真实副作用 |

## 4. 配置名与类型也应表达含义

下面只是自定义配置示意，不是粘贴后会自动接通 MinIO 的完整配置：

```yaml
app:
  storage:
    endpoint: ${MINIO_ENDPOINT}
    bucket: ${MINIO_BUCKET}
    access-key: ${MINIO_ACCESS_KEY}
    secret-key: ${MINIO_SECRET_KEY}
    connect-timeout: 3s
  query:
    max-page-size: 100
```

`app.storage` 是本例自己定义的前缀，需要配置绑定与存储组件消费；`max-page-size` 也需要业务实际检查，写在 YAML 中并不会自动限制接口。超时需要传入对应客户端设置，不是名称里写了 timeout 就一定生效。

为同一组参数建立结构化配置对象时，可考虑 `@ConfigurationProperties`：将地址、Bucket、凭据与超时集中绑定，使用合适的类型并按需校验。少量独立参数也可以使用 `@Value`；不要把“所有地方都必须用某一个注解”写成唯一正确方式。[配置绑定对比](https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.vs-value-annotation)

超时优先用能表达时间单位的类型，例如 `Duration`；数量、容量、比例也应明确单位和允许范围。避免同一 `timeout=3000` 在不同组件中分别被当作秒与毫秒。

## 5. 缺失与错误配置要尽早暴露

必需的连接地址、Bucket 或凭据缺失时，应有清楚的校验和启动失败信息，或明确的按需功能禁用策略。不能默认连到某个共享生产地址，也不要让空凭据延迟到用户第一次下单时才暴露。

校验配置格式不等于证明服务可用：地址格式合法，不代表网络能访问；账号存在，不代表有正确权限；客户端初始化成功，也不保证每次外部请求成功。可以按依赖重要程度安排连接核验与健康检查，但具体探测频率和启动阻断策略要结合运行要求。

## 6. 凭据不进入公共配置与日志

仓库保留配置结构、用途和无真实凭据的示例，实际值由受控的本机环境、外部配置或部署系统提供。环境变量是一种输入渠道，并不自动等于加密或绝对安全；重点是凭据的可见范围、分发和更新方式。

不要给关键密钥设置一个人人都知道的默认值，并依赖“上线前记得替换”。也不要把整个配置对象打印出来排查问题。只记录经过筛选的非敏感摘要；配置诊断或管理端点同样需要合适的访问控制。

如果真实凭据曾被提交，后来加入 `.gitignore` 或删除当前文件并不清除历史泄露，需按实际暴露范围处理并更新对应凭据。本章不读取或修改本机凭据。

## 7. 同一套参数需要覆盖完整请求路径

MinIO 的例子尤其直观：后端可以访问内部地址，前端收到的预签名 URL 却可能指向一个浏览器无法连接的入口。检查外部域名、代理和签名方式时，要沿真实请求路径验证，而不是只看服务端连通。

数据库连接超时、连接池等待超时、SQL 执行时间、整个 HTTP 请求超时，也不是同一个参数。修改某个超时前先确认限制的是哪一段，避免只是把等待时间放大，掩盖连接泄漏或慢查询。

配置只放参数，业务服务决定用途，技术组件把参数接到客户端。沿用第一章的职责分工，不把所有参数读取和连接初始化散落到各个 Controller。

## 8. 在真实项目怎样验证

先列出参数名、类型、用途、是否必需、从哪里注入以及安全的示例值。再用独立测试配置验证缺失、非法和正确输入时的表现，确认实际连接目标与当前 Profile。不要通过打印完整连接串和密钥“证明配置正确”。

当前只有学习材料，没有修改本机 JDK、Maven、Shell 或中间件配置，也未连接任何外部服务。第六章再将配置与实际启动、部署和运行排查连起来。
