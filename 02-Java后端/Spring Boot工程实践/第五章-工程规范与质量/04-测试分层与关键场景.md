# 测试分层与关键场景

所属章节：[[00-第五章-工程规范与质量]]。回看：[[创建订单-四种结果与调用链]]、[[01-事务边界与异常回滚]]、[[03-库存并发与请求幂等]]。

本篇说明怎样选择验证证据，不在当前 Markdown 知识库建立一个虚构的可运行应用。测试片段不包含完整数据准备、项目依赖与实现，均为教学示意，尚未执行。

## 1. 测试验证行为，不只是证明代码没有报错

“请求返回 201”只能说明观察到成功响应；还要按场景确认订单内容、库存变化和重复请求的行为。“失败返回 500”也不能自动证明库存已经回滚。

一个有效场景通常包含：明确的初始条件、执行的动作，以及能判断结果对错的断言。JUnit Jupiter 提供断言结果相等、抛出预期异常等能力；`@Test` 标记方法本身不会替你决定应该检查什么。[JUnit 断言说明](https://docs.junit.org/current/writing-tests/assertions.html)

```text
场景：商品库存不足
准备：库存为 5，用户请求购买 6，商品其余条件满足
执行：通过选定的业务入口创建订单
断言：得到库存不足的明确失败；库存仍为 5；没有新增有效订单
```

如果只打印返回值、不核对结果，程序错误也可能让测试“跑完”。如果只断言结果不为 null，也可能遗漏金额、用户归属和库存等核心问题。

## 2. 不同测试观察不同边界

| 方式 | 适合观察什么 | 单独通过还不能证明什么 |
| --- | --- | --- |
| 单元测试 | 一段业务规则在明确输入下的结果，通常不启动完整 Spring 或真实中间件 | Spring 代理、真实 SQL、数据库约束与网络行为 |
| Web 切片测试 | 参数转换、校验、状态码、响应、异常处理等选定 Web 范围 | 真实 Service、数据库事务及全部运行配置 |
| 数据访问集成测试 | Mapper/XML、数据库类型、约束和关键 SQL | 完整接口权限链或所有业务分支 |
| 业务集成测试 | Spring Bean、事务、数据库和选定外部组件如何协作 | 全部真实部署与客户端行为 |
| 端到端测试 | 从真实请求入口观察关键完整链路 | 所有边界都覆盖；通常运行更慢、定位范围更大 |

Spring Boot 提供 `@SpringBootTest` 和若干切片测试能力，选择要加载的范围。`@SpringBootTest` 默认也不等于启动真实 HTTP 端口；实际模式由配置决定。注解所在依赖和包名要按项目版本核对。[Spring Boot 应用测试](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html)

不必让所有测试都启动完整应用，也不能用大量纯单元测试代替关键集成验证。优先让常见规则反馈快，再对代理、SQL、事务和外部协议等边界补充相应证据。

## 3. Mock 帮助隔离，但不会模拟所有现实

测试订单 Service 时，可以让商品查询替身返回“可售商品”，让 Mapper 替身返回指定结果，从而集中检查业务分支。Mock 的返回值和异常是你设置的，不是一次真实数据库执行。

例如，验证“库存 Mapper 被调用一次”可以帮助确认交互，但不能证明 SQL 条件正确、影响行数符合真实数据、数据库事务生效或并发下没有超卖。若把所有依赖都设为成功，再只检查返回非空，几乎没有验证实际失败风险。

同样，直接 `new OrderService(...)` 调用方法，并不会因为方法上有 `@Transactional` 就自动建立 Spring 事务代理。事务验证要经过真实配置的代理入口，见 [[02-事务代理与业务流程组织]]。

## 4. 创建订单优先关注哪些结果

| 场景 | 应核对的关键结果 | 需要的验证范围 |
| --- | --- | --- |
| 数量为 0 或缺少商品 ID | 明确输入失败，没有进入不应执行的写入 | 输入规则与 Web 校验 |
| 商品不存在、已下架 | 业务失败类型正确，无有效订单 | Service 规则；必要时接口响应 |
| 正常购买 2 件，库存原为 5 | 订单归属、数量、金额和快照正确，库存变为 3 | 规则测试与关键集成测试 |
| 扣减成功但订单保存失败 | 相关数据库变更按预期回滚 | 真实事务与数据库验证 |
| 相同业务请求重复提交 | 不产生重复有效订单，结果符合约定 | 持久化约束和幂等路径 |
| 多请求争抢有限库存 | 不超卖，有效订单与库存变化相符 | 有控制的真实并发场景 |
| 下单用户尝试取消他人订单 | 被拒绝，目标订单和库存不应改变 | 数据权限与业务链路 |

这些是订单案例的优先项，不是每次小修改都必须重跑全部系统测试。依据变更触及的规则、边界和潜在后果选择范围；新增或修复关键行为时，应有能检出该问题的验证。

## 5. “回滚测试通过”也可能有误判

Spring 的测试事务可以在测试方法结束后回滚，用于清理测试数据；这不等于已经证明业务方法自己的事务配置正确。若业务恰好加入测试提前开启的事务，可能遮住生产入口没有正确事务边界的问题。

需要针对目标设计测试：通过正确业务入口触发失败，在合适的独立观察范围核对最终持久化结果，并避免把测试清理动作误当业务回滚。事务提交后的事件或可靠任务，也不能用永远不提交的测试覆盖全部行为。

使用真实 HTTP 随机端口测试时，客户端与服务端通常运行在不同线程，测试线程上的回滚事务不会自动撤回服务端已提交的修改。因此测试数据清理和隔离必须另外安排。[Spring Boot 测试事务边界](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html)

## 6. 数据与执行时序要可控

测试使用独立资源和固定、可辨识的数据：不能依赖共享数据库里“刚好有商品 1001”，也不让用例按偶然的执行顺序才通过。每个场景应明确初始化与清理，资源隔离见 [[03-配置管理与环境隔离]]。

时间相关规则可通过可替换的时钟或指定时间建立边界，而不是等真实时钟走到某一刻。异步和并发场景可控制关键执行时序，并设合理的等待上限；不要随意睡几秒就认定后台处理完成。

使用替代数据库时要意识到 SQL 方言、索引、锁和约束行为可能不同。验证 MySQL 专属 SQL、事务和并发时，应使用与目标足够一致的数据库版本和配置，而不是仅凭内存数据库通过就宣布完成。

## 7. 缓存与文件流程怎样接入测试

第四章提供的失败场景可以沿用：缓存未命中和写后失效、并发旧值回填、Redis 超时与重试；文件上传成功但数据库失败、重复确认、私有下载权限、换图与回收。

客户端 Mock 适合检查“SDK 报错时业务如何处理”；真实测试存储更适合验证对象是否实际存在、签名访问与重复上传的行为。两者提供不同证据，不能互相替代。外部调用重试还要核对是否造成重复副作用。

## 8. 覆盖率、回归与失败处理

覆盖率说明代码被执行到的程度，不能单独证明断言有价值、并发正确或业务边界完整。不要为了数字给每个简单 getter 添加机械测试，却遗漏库存和权限。

修复缺陷时，尽可能先形成能重现原问题的场景，确认修复后通过，再运行受影响的回归范围。失败时先判断是产品行为缺陷、测试数据问题还是环境故障；不能直接删除断言、跳过测试或把错误状态改成“成功”来消除红色结果。

自动测试、静态检查、人工阅读和必要的真实操作互相补充。测试报告中应说明执行了哪些场景、什么环境、结果与未覆盖部分；“未执行”不能写成“已通过”。构建命令如何衔接这些测试，见下一篇。
