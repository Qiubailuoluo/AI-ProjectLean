# 依赖管理与交付检查

所属章节：[[00-第五章-工程规范与质量]]。前置：[[04-测试分层与关键场景]]。本篇命令与 POM 片段仅供阅读，没有在当前知识库执行构建、下载依赖或更改本机工具。

## 1. 引入一个库，实际引入什么

Maven 通过 `groupId`、`artifactId`、`version` 等信息定位依赖。应用在 POM 中声明直接依赖，而这个库可能继续引入其他库，形成传递依赖树。因此“只增加一行依赖”也可能改变应用的日志、JSON 或网络客户端组合。

需要说明它解决什么问题、现有依赖是否已提供同类能力、运行环境是否兼容，以及增加了哪些传递内容。不要因为 AI 的新示例用了另一套库，就把项目已有方案全部替换。

## 2. dependencyManagement 与 dependencies

| 配置位置或方式 | 作用 | 容易误解的地方 |
| --- | --- | --- |
| `dependencies` | 声明当前项目需要的依赖 | 版本可能来自父 POM 或版本管理，而非每条都手写 |
| `dependencyManagement` | 管理遇到相应依赖时应采用的版本等信息 | 仅放在这里，不等于依赖已加入应用 |
| BOM 导入 | 复用一组协调的依赖版本管理 | 不等于自动引入全部依赖，也不等于管理全部插件 |
| Maven 构建插件 | 执行编译、测试、打包等构建任务 | 插件配置与应用运行库不是同一类依赖 |

Spring Boot 的每个版本提供协调过的一组依赖版本。沿用已有 parent 或导入适配的 BOM 时，受管理的库通常无需单独指定版本；未被管理的库仍需适当声明。导入 `spring-boot-dependencies` 也不等同于继承 Boot parent 提供的所有构建默认值。[Spring Boot 构建与依赖管理](https://docs.spring.io/spring-boot/reference/using/build-systems.html)

下面假设项目已正确采用适配的 Spring Boot 依赖管理，是 POM 内的局部片段：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

没有写版本是因为它在本例前提下受管理，不是 Maven 自动知道所有库的最佳版本。测试依赖也不应被当作业务实现长期使用的运行时能力。

## 3. 版本冲突不按“越新越优先”解决

多个依赖间接带入同一库的不同版本时，Maven 会结合版本管理和依赖调解选择实际版本。没有其他管理约束时，普通传递依赖冲突常采用路径更近的定义；同深度还有声明顺序等规则。不能只看自己手写的一条版本就确定最终结果。[Maven 依赖机制](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html)

可以查看以下信息，命令是教学示例：

```sh
mvn dependency:tree
mvn help:effective-pom
```

依赖树帮助确认库从哪里引入，最终生效的 POM 帮助确认继承和管理结果。必要时按目标库筛选输出，避免只看庞大文本的第一屏。

排查时先找到来源和冲突原因，再评估统一版本、替换组件或定向 exclusion。不能看到冲突就随意排除一串传递依赖；编译暂时通过，也可能在运行时出现缺类、缺方法或日志实现冲突。

## 4. Scope 与兼容性

| 常见 Scope | 大致用途 | 本例要注意什么 |
| --- | --- | --- |
| `compile`，默认值 | 编译和运行需要的普通依赖 | 不把所有工具都默认放进运行范围 |
| `runtime` | 编译源码通常不直接需要，但运行需要 | 例如部分驱动选择，仍按实际打包核对 |
| `test` | 测试编译和执行使用 | 不把业务代码写成依赖测试库才能运行 |
| `provided` | 编译需要，运行时预期由指定环境提供 | 需结合容器与打包方式判断，不能随意照抄 |

Java 版本、Spring Boot 大版本、第三方 starter、SDK、驱动与插件需要配合。不能将不同年代示例的依赖、注解包名和构建配置拼起来，再通过不断升级来碰运气。

官方系统要求会随版本变化。实践前先读取项目现有 POM、构建说明和目标部署环境，再核对对应版本要求；当前文档链接默认版本不构成升级建议。[Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)

本机已有 JDK 与 Maven 的管理约定，实践时按项目要求选用；本次不重新安装、不改全局版本，也不修改 Maven 镜像或本地仓库设置。

## 5. Maven 命令分别证明什么

以下命令应在真实 Maven 项目中按其构建约定使用；本知识库当前没有应用 POM，不在这里运行：

| 命令示例 | 通常推进到哪里 | 不能据此直接认定什么 |
| --- | --- | --- |
| `mvn compile` | 编译主源码 | 测试通过、应用能够正确处理业务 |
| `mvn test` | 编译并执行测试阶段中配置的任务 | 集成测试、打包与部署均已完成 |
| `mvn package` | 执行前序阶段并打包 | 所有集成测试、静态分析和真实启动都已验证 |
| `mvn verify` | 执行到验证阶段及其绑定的检查 | 项目没有配置的检查也会自动出现 |
| `mvn install` | 将构建产物安装到本机 Maven 仓库 | 启动或部署了业务应用 |

同一生命周期内，调用后面的阶段会推进经过前面的阶段；具体执行哪些任务取决于插件绑定、测试发现规则和跳过参数。`clean` 属于另一条生命周期，清理构建输出，并不是每次小改动都必须使用。[Maven 构建生命周期](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html)

项目若配置 Failsafe 运行集成测试，通常通过 `verify` 推进完整集成验证与收尾，而不是只调用 `integration-test` 后就停止。但不是每个项目都已经配置了 Failsafe。[Maven Failsafe](https://maven.apache.org/surefire/maven-failsafe-plugin/)

项目提供 Maven Wrapper 时，可按其说明使用 `./mvnw`，使构建工具版本更可控；仍需要匹配 Java、配置与外部测试资源。命令成功后还要看实际运行了多少测试、是否被跳过，以及质量检查是否真正执行。

## 6. 一次升级怎样控制范围

先说明升级的原因：修复已确认问题、满足必要能力或适配目标环境。读取对应版本的变化与兼容说明，核对直接依赖、传递依赖和插件，再运行受影响的规则与集成场景。

不要同时升级整个技术栈、调整全部目录和重写业务，再用“启动成功”作为唯一证据。可以按有联系的变更分步完成，让故障来源更容易定位。固定依赖与插件版本、记录环境和构建方式，有助于复现；本身并不保证所有运行环境和构建结果完全一致。

## 7. 怎样审查 AI 交付的修改

围绕一次具体需求，例如“取消订单时可靠返还库存”，按结果检查：

1. 是否明确了允许取消的状态、当前用户权限、重复请求与失败结果。
2. 是否沿用已有模块职责和错误约定，避免 Controller 直接绕过必要规则。
3. 是否保留正确事务边界；Redis、MinIO、远程调用等副作用是否有适当恢复方式。
4. 是否在触及输入、SQL、状态、配置或依赖时同步核对相应契约，而非只改返回文案。
5. 是否有能检出原问题的测试或验证，关键结果是否核实；未运行的范围有没有明确列出。
6. 修改是否夹带无关格式重排、依赖升级或配置变更，使真正行为难以审查。

这是一种审查思路，不是要求每次改一行文字都执行全系统流程。已有项目的明确要求应遵循，验证范围与变更影响相称。不能通过放宽业务校验、删除失败测试或吞掉异常来制造“检查通过”。

## 8. 什么样的完成说明可供判断

好的说明包含：解决了什么触发条件、现在有什么行为、实际改动范围、运行了哪些验证及结果、还有什么未验证或依赖外部条件。比如“库存不足场景已通过单元测试；真实 MySQL 并发未验证”，比笼统的“全部完成，无问题”更有用。

日志、配置、测试和依赖应随行为变化一起检查。持续集成可自动执行已配置的构建与检查，但不会自动理解业务正确性；没有实际接入的格式检查、静态分析或依赖风险检查，不应写进“已执行”报告。
