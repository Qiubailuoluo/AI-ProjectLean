# 构建产物与启动参数

所属章节：[[00-第六章-部署与运行]]。回看：[[05-依赖管理与交付检查]]、[[03-配置管理与环境隔离]]。

## 1. 源码、构建与可执行产物

开发时在 IDE 运行，与发布一个可执行 JAR，不是相同的启动路径。IDE 可能提供了源码目录、运行时依赖、环境变量和额外参数；不能据此认定换一台机器双击任意 JAR 就能启动。

Maven 的 `package` 阶段负责按项目配置打包；Spring Boot Maven 插件的 `repackage` 可以生成包含应用依赖的可执行归档。是否真正绑定执行，要看实际 POM，不能只见到插件名字就认定已经生成了正确产物。[Spring Boot 可执行归档](https://docs.spring.io/spring-boot/maven-plugin/packaging.html)

```text
源码与构建配置
    → 编译、测试和已配置的检查
    → 打包与可执行归档处理
    → 明确标识的应用产物
```

应核对构建日志、实际测试结果和输出文件用途。普通库 JAR、原始归档、可执行 JAR、源码包与测试包不能仅按扩展名 `.jar` 混用。当前采用可执行 JAR 教学，不要求额外安装外部 Tomcat；WAR、容器镜像等按项目需要另行选择。

## 2. 构建成功与可运行需要分别证明

构建成功说明配置的构建任务通过，不等于目标机器的 Java、网络、凭据或数据结构已经满足要求。先记录源码提交、构建工具与 Java 版本、依赖和产物标识，再核对目标运行环境。

编译目标与运行 JDK 不匹配，可能出现不支持的 class 版本；使用了特定本机库或镜像时，还要核对操作系统与 CPU 架构。不要看到启动错误就同时升级 JDK、Spring Boot 和全部依赖来碰运气。

本机已有 JDK 与 Maven 的管理约定，实践时按真实项目需求选用，本次不修改这些全局配置。

## 3. JVM 参数与应用参数的位置不同

命令仅为示意，文件名、端口和内存都不是固定推荐值：

```sh
java -Xms256m -Xmx512m -jar shop-demo.jar \
  --spring.profiles.active=dev \
  --server.port=8080
```

`-Xms`、`-Xmx` 在这里属于 JVM 参数，放在 `-jar` 之前；JAR 后面的 `--spring...` 和 `--server...` 是传给应用的参数。把 JVM 参数放到 JAR 后面，并不能按预期设置 JVM 堆。[Java 启动命令](https://docs.oracle.com/en/java/javase/17/docs/specs/man/java.html)

`-Xmx512m` 限制的是 Java 堆上限，不是整个 Java 进程只能使用 512 MB。线程栈、元空间、直接内存等仍会占用资源，容量需要按负载和运行限制验证。

## 4. 启动前应明确哪些输入

| 输入 | 订单案例要确认什么 |
| --- | --- |
| Profile 与外部配置来源 | 确实是目标环境，而非意外连到另一个库 |
| 数据库与结构版本 | 地址、权限、连接参数与本次 SQL 相容 |
| Redis 与 MinIO | 必要能力和故障策略符合业务要求，不能只测连接 |
| 工作目录与文件路径 | 相对路径从哪里解释，是否有目录与文件权限 |
| 对外入口与内部端口 | 应用监听、代理上游和客户端访问地址相互对应 |
| 日志与关联标识 | 启动失败和业务异常能留下可定位证据 |

配置覆盖顺序、密钥来源和校验方式见第五章，不在启动命令里粘贴真实密码。敏感参数出现在命令行还可能进入命令历史或进程信息，应按环境采用受控配置渠道。

## 5. 前台学习运行与长期进程管理

首次在隔离环境尝试时，前台运行便于查看启动错误和停止行为。长期运行则需要明确进程归属、日志去向、停止信号、退出状态和重启策略，可由适合操作系统的服务管理器或容器平台承担。

`nohup` 或把命令放到后台，只改变终端与进程的关系，不自动提供健康判断、失败重启、版本记录和可靠停止流程。也不要把 Linux 服务管理命令直接照搬到 Mac。

## 6. 如何证明启动的是本次产物

记录实际产物的位置与版本标识，核对运行参数、启动日志、端口、健康结果以及必要的业务检查。只确认“某个 Java 进程存在”，可能观察到的是旧版本或另一个应用。

产物应能关联到构建和源码；运行配置与密钥独立管理。尽量发布已验证的同一份产物，而不是每台机器各自从不同源码状态重新构建。
