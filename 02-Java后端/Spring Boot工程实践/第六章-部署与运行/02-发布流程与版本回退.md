# 发布流程与版本回退

所属章节：[[00-第六章-部署与运行]]。前置：[[01-构建产物与启动参数]]、[[05-依赖管理与交付检查]]。

## 1. 发布不只是替换一个文件

发布需要让目标版本在匹配的配置和数据结构上运行，并按要求接收流量。可以把发布对象理解为“应用产物 + 配置要求 + 数据结构要求 + 运行与回退步骤”。

例如新订单字段已写入代码，但目标数据库还没有该列，JAR 构建成功也可能在首次查询时失败。反过来，数据库字段已经删除，重新启动旧 JAR 也不一定能回退成功。

## 2. 一个适合学习的发布闭环

以下是流程示例，不是在任何真实环境执行的操作：

1. 明确需求与变更范围，确认配置、数据结构和外部依赖要求。
2. 从确定的源码状态构建，执行已配置的测试与质量检查。
3. 记录产物版本、构建来源与完整性信息，保留可恢复的旧版本。
4. 在匹配的隔离环境验证启动、代表性接口和关键业务结果。
5. 按选定策略启动新版本并检查就绪，再切换或逐步引入流量。
6. 观察错误率、耗时、任务积压与业务结果，确认是否继续、暂停或回退。
7. 旧实例按停机流程退出，记录实际发布结果与尚未解决的问题。

代表性业务检查应考虑副作用，不能为测试生产入口随意创建真实订单、发送通知或删除文件。健康检查与应用验证各有用途，见 [[04-健康检查与优雅停机]]。

## 3. 不同发布策略解决什么

| 方式 | 简化理解 | 需要接受或处理的条件 |
| --- | --- | --- |
| 停旧再启新 | 单实例替换后重启 | 存在不可用窗口；需处理进行中的请求与任务 |
| 蓝绿 | 保留两套版本，准备好后切换入口 | 额外资源、配置与数据兼容；流量切回不等于数据回滚 |
| 滚动 | 逐个替换多个实例 | 一段时间内新旧实例并存，接口和存储需兼容 |
| 小流量验证 | 先让部分流量进入新版本再观察 | 流量选择、观测和退出策略明确，不能用少量成功请求证明全部正确 |

这是选择思路，不要求学习项目一次实现全部方式。单实例可以先建立明确发布和回退记录，再根据可用性、容量与变更频率选择更多机制。

## 4. 新旧版本并存时要考虑哪些契约

请求与响应、数据库字段、Redis 缓存结构、后台任务载荷和文件记录，都可能跨版本流转。旧实例读取新格式缓存，或新实例处理旧任务，都可能暴露兼容问题。

数据结构变更可按需要考虑“先扩展兼容结构 → 发布能兼容的应用 → 分批迁移与观察 → 确认旧版本退出后再收缩”。例如重命名一个业务字段，可能需要过渡读取或写入策略，不能把数据库列和所有应用瞬间替换视为理所当然。

具体迁移要有版本、执行记录和失败处理。使用版本化迁移工具也不代表可以任意执行破坏性变更；迁移过程中耗时、锁和数据量会影响运行。

## 5. 回退应用不等于撤销已经发生的业务

恢复旧产物不能自动撤回已提交订单、已发送通知、已上传文件或已修改的数据。数据库备份也不是对某一用户操作的简单“撤销键”：整体恢复可能丢失之后的有效业务，还涉及服务暂停和其他存储的一致性。

| 变化 | 回退前要确认什么 |
| --- | --- |
| 只改应用逻辑 | 旧版本仍能读取当前数据与配置吗？ |
| 数据结构已变化 | 旧 SQL 是否相容，有没有不可逆变更？ |
| 缓存或任务格式变化 | 旧版本能否识别，是否需要隔离或兼容处理？ |
| 外部副作用已发生 | 是否需要业务补偿，而非重放旧代码？ |

某些问题适合小范围修复后向前发布，某些适合切回旧版本；选择由业务影响、兼容性和恢复时间决定，不能把“有旧 JAR”当作所有变更都能立即回退。

## 6. 什么情况下停止继续发布

可根据发布前约定观察明显的错误增加、响应恶化、核心结果不正确或任务持续积压。阈值应结合真实基线和负载，不采用没有依据的固定数字。

出现问题时保留版本、配置来源、时间范围、关联日志和业务证据，先控制影响再定位。不能为了让发布“完成”，临时关闭必要校验、绕过权限或忽略数据库失败。

## 7. 记录一份能够复现的发布结果

至少能回答：发布了哪个产物、使用哪套非敏感配置说明、是否包含数据迁移、怎样验证、何时切流、观察到什么，以及回退条件与实际结果。凭据本体不写入记录。

本章尚未制作真实发布脚本、配置迁移工具或执行回退。后续用一个隔离项目验证这个闭环，再选择是否自动化。
