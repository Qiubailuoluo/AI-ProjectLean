# 反向代理与访问路径

所属章节：[[00-第六章-部署与运行]]。通用概念见 [[部署基础与请求链路]]，这里集中看 Spring Boot 接口与代理的衔接。

## 1. 先画清楚每一段地址

假设对外请求为 `/api/orders`，应用 Controller 映射为 `/orders`，应用没有额外上下文路径。代理需要按约定移除 `/api/` 前缀，才能让后端收到预期路径。

反向代理不是业务 Service，它转发请求，不代替商品规则、订单数据权限或数据库事务。静态页面加载成功，也不能证明这段 API 转发正确。

## 2. proxy_pass 是否带 URI 会改变结果

以下是普通前缀 location 的局部教学配置，两段是替代方案，不是同时粘贴到同一 server 的完整配置；端口仅为示例，未修改本机 Nginx。

```nginx
# 方案 A：proxy_pass 带 URI “/”，替换匹配到的 /api/ 前缀
location /api/ {
    proxy_pass http://127.0.0.1:8080/;
}
```

```nginx
# 方案 B：proxy_pass 不带 URI，按相应规则保留请求 URI
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

| 普通请求 `/api/orders` | 上游收到的路径 | 适用前提 |
| --- | --- | --- |
| 方案 A | `/orders` | 应用实际映射 `/orders` |
| 方案 B | `/api/orders` | 应用实际映射包含 `/api` |

差别来自 URI 替换规则，不是“一切场景都必须加斜杠”。正则 location、rewrite、变量和其他配置会影响处理方式，不能机械套用上表。[Nginx proxy_pass 规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)

若 Spring Boot 还有 `/shop` 上下文路径，也需一起计算最终请求路径。不要让前端 API 前缀、代理替换和应用映射分别各猜一次。

## 3. 域名、HTTPS 与转发信息

TLS 可以在入口终止，再由入口访问后端；具体是否加密每一段取决于网络与部署要求。外部协议、主机名和客户端地址经过代理后可能与后端直接观察的连接不同。

应用生成跳转、绝对链接或安全相关判断时，可能需要正确处理转发信息。是否使用容器原生或框架的 forwarded headers 支持，按 Spring Boot 版本和可信代理边界配置；不能无条件把任意客户端提供的转发头当作可信身份或来源。

浏览器跨域策略、Cookie 条件和登录授权也要与真实外部地址配合。不能看到 401 或 403 就先放开全部权限，或者看到跨域报错就认定后端没有收到请求。

## 4. 超时要区分是哪一段

| 超时或限制 | 大致关心什么 |
| --- | --- |
| 连接上游超时 | 入口能否及时建立到后端的连接 |
| 上游响应读取超时 | 入口在读取后端响应时等待数据的条件 |
| 应用到数据库或外部服务超时 | 业务内部依赖调用的等待 |
| 客户端超时 | 用户端愿意等待多久，可能先于服务端处理结束 |

例如 Nginx 的 `proxy_read_timeout` 是相邻读取操作之间的超时，并非整个响应传输总时长的统一上限。不能把某个参数改大就宣称整个请求链路的超时都解决了。[Nginx 读取超时](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)

客户端或代理超时不等于订单业务确定失败。重试前需要幂等和结果确认，见 [[03-库存并发与请求幂等]]。

## 5. 常见表现应怎样缩小范围

| 表现 | 优先核对的方向，非唯一原因 |
| --- | --- |
| 外部连接失败 | DNS、网络、TLS、入口监听与访问条件 |
| 404 | 哪一层返回，代理后的路径与应用映射是否相符 |
| 401 / 403 | 凭证是否传递，认证入口和业务权限是否正确 |
| 413 | 入口和应用各自的上传大小限制 |
| 502 | 上游连接、协议、响应与实例状态 |
| 504 | 上游等待与应用内部耗时，必要时关联数据库与外部调用 |

先用关联日志和相同请求确认错误来自哪一层。应用本地接口正确、代理请求失败，可以缩小到转发和入口；应用本地也失败，就继续检查应用与依赖，不要同时大改所有配置。

## 6. 长连接、上传与配置生效

WebSocket、流式响应、大文件上传等可能需要额外的协议、缓冲与超时设置。普通小 JSON 接口可用的代理片段，并不自动成为这些场景的完整配置。

配置改动后需按实际安装方式检查语法、核对生效文件并重新加载。语法通过仅说明配置结构满足检查，不证明目标后端可用或路径正确。[Nginx 启动与配置加载](https://nginx.org/en/docs/beginners_guide.html)
