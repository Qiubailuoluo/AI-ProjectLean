# 健康检查与优雅停机

所属章节：[[00-第六章-部署与运行]]。回看：[[02-发布流程与版本回退]]、[[04-失败恢复与可靠任务]]。

## 1. 四种“正常”不是一回事

| 判断 | 回答什么 | 不能单独证明什么 |
| --- | --- | --- |
| 进程存在 | 程序尚未退出 | Web 线程能处理请求、依赖正常 |
| 端口可连接 | 某个监听端点能够建立连接 | 本次业务规则和数据库操作正确 |
| 健康或就绪检查通过 | 已配置的检查当前满足条件 | 未检查的功能、配置和数据都正确 |
| 代表性业务验证通过 | 某条真实链路获得预期结果 | 所有业务场景和持续负载都已覆盖 |

“日志出现 Started”是启动证据之一；还需要根据目标验证配置、请求链路和关键行为。不要把一个固定返回 200 的健康接口作为整个订单系统的正确性证明。

## 2. Actuator 提供运行观察入口

Spring Boot Actuator 可以提供健康、指标及其他管理能力。端点是否存在、是否暴露和谁能访问，需要结合依赖、配置、安全规则与版本核对；写了一个路径不等于功能已经接通。[Actuator 端点](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)

局部教学配置示例，未执行：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      show-details: never
```

这不是完整的管理面保护方案，也不意味着所有人应该能访问其他管理端点。不要为了排查方便直接暴露全部端点；某些端点包含运行信息或可执行管理动作，访问范围需明确。

## 3. 存活与就绪要分开理解

存活（liveness）关注应用是否陷入需要重启才能恢复的内部失常；就绪（readiness）关注当前是否适合接收流量。二者可以驱动不同的平台动作，不能把所有依赖异常都映射成“重启应用”。

假设共享数据库暂时不可用，重启全部应用实例通常不会修复数据库，还可能加重恢复压力。存活检查不应简单依赖共享外部系统。就绪是否检查某个依赖，则要看它是否必需、是否存在降级及撤走所有实例的后果。[Spring Boot 探针与外部依赖](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes)

Kubernetes 是可采用这些信号的一种平台，不是本章要求安装的前提。实际探针路径、启用条件和接流量规则需按所用版本与平台配置。若管理端口与业务端口分离，还要考虑管理端口健康但业务端口已阻塞的情况。

## 4. 优雅停机要保护进行中的工作

直接结束进程，可能中断正在处理的请求、缓存失效任务或文件操作。优雅停机希望停止接收新工作，同时给正在执行的工作合理时间完成；它不是让所有任务无期限运行。

可以将发布退出过程理解为：从入口撤走旧实例或使其不再就绪 → 考虑状态传播与连接处理 → 发送适当停止信号 → 在时间预算内处理现有工作 → 关闭资源并退出。实际顺序与协调方式取决于入口和进程管理器，不是只设一个属性就自动控制整条链路。

Spring Boot 支持 Web 应用的优雅停机。局部配置示意：

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

这里的 20 秒是示例且按停机阶段配置，不是所有应用的推荐值，也不是整个系统退出过程永远只有 20 秒。默认行为和具体 Web 服务器处理方式按项目版本确认。[Spring Boot 优雅停机](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)

## 5. 退出信号与时间预算必须配合

进程需要有机会收到并处理适当的终止信号；强制结束不能指望应用执行清理回调。IDE 的停止按钮、服务管理器和容器平台的实际行为也可能不同。

应用各阶段预算、外层进程管理器强制终止时间、入口连接与外部调用超时，需要一起考虑。外层过早强制退出，应用内部配置再长也没有意义。若业务工作长期超时，应考虑任务化、拆分或恢复机制，而不是无限延长停机等待。

## 6. 后台任务与重试仍然需要可靠设计

Web 请求停止接收，不代表后台调度、消息处理或可靠任务自然停止领取新工作。需要按组件生命周期停止领取、等待或安全中断，并让未完成工作能在后续恢复。

若通知已经发出但成功状态尚未记录时退出，重启后仍可能再次执行，因此幂等与持久化任务设计不能省略。优雅停机降低中断风险，不提供“永不重复、永不丢失”的自动保证。

## 7. 怎样验证而不是只看配置

在隔离环境下分别观察：启动期间是否被过早接流量、就绪变化是否被入口识别、进行中请求遇到正常停止时怎样结束、超时任务能否恢复，以及应用依赖故障时是否出现不合理重启。

检查健康失败和成功的实际含义，而不仅是状态码。必要业务验证使用受控数据与副作用范围。当前未启动 Actuator、发送终止信号或操作进程。
