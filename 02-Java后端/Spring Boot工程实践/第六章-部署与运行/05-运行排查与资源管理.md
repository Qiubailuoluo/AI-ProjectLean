# 运行排查与资源管理

所属章节：[[00-第六章-部署与运行]]。回看：[[02-日志设计与问题定位]]、[[05-慢查询定位与优化验证]]、[[部署基础与请求链路]]。

## 1. 先描述现象与范围

先明确什么时候开始、哪些请求受影响、是否只有某个版本或实例、表现为错误还是变慢，以及最近改变了什么。保留关联标识、配置来源和必要证据，再根据影响选择暂停发布、限制流量或其他恢复方式。

不要一遇故障就同时重启应用、清空缓存和修改连接池。偶然恢复不能说明根因已经解决，大范围改动也会破坏排查线索。

## 2. 启动失败按所处阶段检查

| 现象或证据 | 优先核对方向 |
| --- | --- |
| 找不到主类或不可执行归档 | 是否用了正确产物，构建插件和启动方式是否匹配 |
| class 版本不支持 | 构建目标与运行 JDK 是否兼容 |
| 端口绑定失败 | 监听地址、端口占用及实际进程归属 |
| 配置绑定、占位符或 Bean 创建失败 | 有效配置、Profile、必要参数和组件条件 |
| 数据库或外部客户端初始化失败 | 网络、凭据、权限、服务状态及所需功能 |
| 迁移或 SQL 错误 | 数据结构版本、数据库版本与迁移执行结果 |

这张表是排查起点，不是仅凭异常最后一行就能下结论的映射。结合完整异常链、启动阶段和最近变更确认原因，不把框架包装的异常名当成全部根因。

## 3. 请求失败沿链路逐段缩小

先检查外部入口与应用本地表现是否一致，再定位认证、参数校验、业务、数据库或外部服务。HTTP 错误可能由代理或应用产生，不保证所有响应都有应用约定的 `code` 和 `message`。

数据库连接或提交故障后，结果可能不确定。应用响应失败、客户端超时和业务没有发生不能直接画等号；先查询实际状态，再按幂等约定重试。

## 4. 请求变慢不一定是 SQL 慢

```text
一次请求的等待可能发生在：
入口排队 → Web 线程 → 数据库连接池 → SQL 与锁
       → Redis / 文件存储 / 外部接口 → 序列化与网络返回
```

关联日志、调用链和指标帮助定位等待在哪一段；慢查询日志与执行计划只覆盖其中一部分。既不能所有问题都怪索引，也不能看到 CPU 不高就认定应用没有瓶颈。

观察请求数量、错误率、耗时分布与并发变化。平均耗时正常时，仍可能有一部分请求长时间等待；分位数能补充观察尾部表现，但也需结合样本量和时间范围。

## 5. 常见资源分别看什么

| 资源 | 需要观察的现象 | 不宜直接采用的结论 |
| --- | --- | --- |
| CPU | 哪些实例、线程在消耗，是否与流量或循环有关 | CPU 高就只扩机器 |
| Java 堆与 GC | 对象增长、回收行为、停顿与负载关系 | 加大堆就能修复所有内存问题 |
| 进程或容器总内存 | 堆外、线程、直接内存与运行限制 | Xmx 就是进程总内存上限 |
| Web 与任务线程 | 排队、阻塞、耗尽及任务执行时长 | 线程越多吞吐量一定越高 |
| 数据库连接池 | 使用量、等待、超时、未释放连接和事务长度 | 把连接池改到很大就能解决慢 SQL |
| 磁盘 | 日志增长、临时文件、诊断文件与可用空间 | 随意删除运行中的日志或业务文件 |

Java 堆内存不足、操作系统因总内存限制结束进程，可能呈现不同证据。具体诊断手段按 JDK、操作系统与运行方式选择，不混用未经核对的参数。

## 6. 多实例会把局部上限相加

若每个实例允许最多若干数据库连接，增加实例会相应增加潜在连接需求，还要为后台任务、其他应用和管理操作留出容量。单实例配置看起来正常，也可能在扩容后压满共享数据库。

线程池、连接池、队列和外部服务容量要配合。队列无限增长或超时无限放大，可能只是把立即失败变成更长的等待和更多内存占用。先明确可承受的并发、超时和降级，再验证配置。

## 7. 诊断文件与临时调整要有边界

线程转储可以帮助观察线程执行和等待，堆转储可以帮助分析对象占用；获取它们可能有资源开销，内容也可能包含业务数据，需受控保存与分析。不能为了诊断把文件公开上传或永久堆在运行磁盘。

临时提高日志级别、修改阈值或限制流量，应记录时间、范围、效果与恢复方式。故障结束后检查是否仍保留临时设置，不用永久 DEBUG 或忽略错误来维持“看起来正常”。

## 8. 从恢复到复盘

恢复服务后核对数据与后台任务是否仍有未完成或结果不确定的部分。保存触发条件、证据、根因、修复、验证与后续观察，不将“重启后正常”直接写成根因。

将能检出问题的场景补到适合的测试或运行检查中，说明仍未覆盖的范围。按需求修复配置、代码、资源预算或发布流程，而非只增加一份没人看的文档。
