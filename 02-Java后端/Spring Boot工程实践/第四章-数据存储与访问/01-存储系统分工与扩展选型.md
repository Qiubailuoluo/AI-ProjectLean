# 存储系统分工与扩展选型

所属章节：[[00-第四章-数据存储与访问]]。

| 系统 | 组织方式 | 常见用途 |
| --- | --- | --- |
| MySQL | 关系型数据库，表、行、列 | 用户、商品、订单、权限等业务事实 |
| Redis | key 对应不同结构的 value | 缓存、验证码、计数、短期请求占位 |
| MinIO | Bucket 中的 Object | 图片、视频、PDF、附件等文件 |

Redis 不限于简单字符串，支持 Hash、List、Set、Sorted Set 等结构；MinIO 更准确地说是对象存储，不只保存图片。Redis 有持久化能力，MySQL 也能存二进制文件，技术上能存不等于适合当前职责。

## 商品详情的分工

- MySQL：名称、售价、库存、文件关联信息。
- MinIO：文件内容，以桶与对象键定位。
- Redis：按需要存商品详情缓存副本。

例如桶 shop-assets、对象键 products/1001/cover.jpg。斜杠表现类似目录，不应完全等同本地文件系统。数据库可以记录桶、对象键或文件 ID，不把会过期的临时访问链接当永久文件位置。

## 按需引入，而非配齐组件

常规项目可以从 MySQL 开始，有缓存和文件需求再加 Redis、对象存储。每多一个组件，都增加部署、备份、监控和数据一致性成本。

ES 可用于全文搜索、检索分析和日志分析，不是所有项目必须具备。开发或简单部署可先使用控制台、滚动日志，明确保留和清理；多实例检索困难时再考虑集中日志系统，例如 Elastic 相关方案或 Loki。

运行日志不能替代业务记录：异常堆栈与订单取消历史、支付记录承担不同职责。

## 其他类型：当前仅建立认识

- PostgreSQL：关系型数据库选项，常与 MySQL 形成选型替代，不必同时部署。
- MongoDB：文档数据库，按数据模型与查询需求评估。
- ClickHouse：分析型数据库，面向大量分析计算等需求。
- Neo4j：图数据库，面向复杂关系遍历等专项需求。

这些尚未深入学习，不作为当前项目必须引入的依赖。
