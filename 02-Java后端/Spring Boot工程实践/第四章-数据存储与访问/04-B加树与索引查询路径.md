# B+ 树与索引查询路径

所属章节：[[00-第四章-数据存储与访问]]。

## 基础：树、页面与有序查询

当前限定 InnoDB 常见有序索引。B+ 树的非叶子节点主要导航，叶子层存索引记录，并可沿叶子页顺序访问，适合范围查询。节点分支多使树较矮，减少定位经过的页面。

InnoDB 默认索引页大小为 16KB；页面可能已在内存，经过一层不代表一定读一次磁盘。MySQL 官方常以 B-tree 统称这类索引结构。

## 两种索引不是上下嵌套

| 索引 | 叶子记录的简化理解 |
| --- | --- |
| 聚簇索引 | 以主键组织行数据 |
| user_id 二级索引 | user_id 加对应行的主键 |

有主键时 InnoDB 用其组织聚簇索引。两者是独立索引树，不是所谓一级索引与其子树。

```text
按 user_id 二级索引定位记录
           ↓ 取得订单主键 id
访问同一 orders 表的聚簇索引
           ↓
读取缺少的 total_amount 等字段
```

这才是回表方向：二级索引 → 聚簇索引，不是查询别的表。

若只查 user_id 和 id，二级索引已有所需字段，可形成覆盖索引。覆盖描述索引与查询的关系，不是单独树种。实际 MVCC 可见性等细节后续深入，此处不将覆盖等同任何场景绝对不访问聚簇记录。

## 联合索引与最左前缀

索引 (user_id, status, created_at) 先排用户，同用户排状态，同用户同状态再排时间，时间不是全局有序。

可按 (user_id)、(user_id,status)、(user_id,status,created_at) 的左侧连续部分定位。只查 status 通常不能直接像第一个字段那样高效定位，具体计划可能涉及扫描或其他优化，不能说绝对不使用索引。

跳过 status、按用户和时间查，仍可利用用户定位，但时间不直接构成该用户全部状态下的连续范围；后续字段也可能继续参与过滤。

WHERE 条件书写顺序不决定最左前缀，决定因素是索引字段排列。

## 从订单列表设计索引

```sql
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 101 AND status = 'CREATED'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

可评估 (user_id,status,created_at,id)：等值筛选在前、后面配合排序。id 让时间相同时顺序明确；InnoDB 二级索引本就附带主键，具体定义是否显式列出 id 应结合主键及执行计划，不机械增加重复字段。

若不筛选状态，状态夹在用户与时间中间，可能无法直接满足跨状态时间排序，应另行评估 (user_id,created_at,id)。

本查询还要 total_amount，可能回表。只取少量行时可能完全可接受，不为零回表把全部响应字段塞进索引。

索引提高读取效率，也消耗空间并增加写入维护成本。目标是减少整体无效工作，不是索引越多越好。
