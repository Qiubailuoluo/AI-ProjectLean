# 慢查询定位与优化验证

所属章节：[[00-第四章-数据存储与访问]]。

## 排查闭环

用户提出的思路正确：查看慢查询日志 → 对应 Mapper/XML → 复现查询 → 分析与优化 → 用记录验证效果。

准确说通常是查“慢 SQL”，不一定是索引本身慢。

1. 从慢查询日志和应用监控确定具体 SQL，记录时间、频率、耗时、扫描与返回规模等可获得信息。
2. 根据 MyBatis namespace、statement id、调用链等定位 Mapper 与 XML；SQL 也可能来自注解、Provider 或拦截器，并非一定有 XML。
3. 保存真实执行 SQL、绑定参数及类型。XML 里的 if、foreach 等是模板；分页、租户、逻辑删除等插件也可能改写 SQL。不能只复制 XML 模板就认为已复现。
4. 在有代表性的数据、索引、统计信息和版本配置下查看执行计划；补充并发、锁等待和连接等待等因素，不把所有慢请求归因于索引。
5. 提出有依据的查询或索引修改，先验证结果正确性，再比较相同条件下的性能。
6. 记录修改前后计划、实际耗时分布和扫描量，观察真实运行效果。单次本地查询变快不足以证明优化成功。

数据与参数记录按项目敏感信息处理规范保存，不为了复现把真实凭证或个人信息上传仓库。

## 执行计划入门

```sql
EXPLAIN FORMAT=TRADITIONAL
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 101 AND status = 'CREATED'
ORDER BY created_at DESC
LIMIT 20;
```

| 项 | 看什么 |
| --- | --- |
| possible_keys | 可能用于查找的索引 |
| key | 实际计划选用的索引 |
| type | 访问方式 |
| rows | 估计检查行数 |
| filtered | 估计过滤后保留比例 |
| Extra | 补充执行信息 |

- key 有值不等于快，仍可能扫描大量记录。
- Using index 通常指覆盖索引，不是泛指使用了任何索引。
- Using filesort 表示额外排序，不等于一定落盘或一定慢。
- ALL 表示全表扫描，小表或返回大部分数据时可能合理。
- 普通 EXPLAIN 是计划和估算，不是实际执行结果。
- EXPLAIN ANALYZE 会真正执行支持的查询并报告实际数据，不能当作完全不执行 SQL 的观察操作。

## 日常记录建议

| 项目 | 内容 |
| --- | --- |
| 查询来源 | 接口、Mapper statement、业务场景 |
| 查询形态 | 最终 SQL、脱敏参数、参数类型 |
| 环境 | MySQL 版本、表结构、索引、数据量与分布 |
| 基线 | 频率、耗时分布、扫描/返回量、原执行计划 |
| 假设 | 慢的原因与证据，是否涉及锁或资源等待 |
| 修改 | SQL 或索引变更及代价 |
| 验证 | 正确性、同条件性能对照、写入影响 |
| 上线观察 | 是否改善、是否回归、回退方案 |

当前只有学习方案，未检查真实数据库日志、未执行任何真实查询，不能声称已经完成性能优化。
