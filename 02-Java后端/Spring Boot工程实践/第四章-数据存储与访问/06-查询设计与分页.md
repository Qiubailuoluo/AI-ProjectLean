# 查询设计与分页

所属章节：[[00-第四章-数据存储与访问]]。前置：[[04-B加树与索引查询路径]]、[[05-慢查询定位与优化验证]]。

本篇将已讨论的页码分页、深分页和游标条件整理成阅读稿，并补充接口协作与适用边界。SQL 和响应都是教学示例，未连接真实数据库，也未完成性能验证。

## 1. 先确定查询要回答什么

订单列表的需求是：“查看当前用户的订单，最新的排在前面，每页最多 20 条。”先把它拆成四件事，再考虑加索引：

| 查询部分 | 需要明确的内容 |
| --- | --- |
| 返回字段 | 列表需要订单 ID、金额、创建时间，不把所有内部字段都返回 |
| 筛选条件 | 当前用户、可选订单状态；用户身份从后端认证上下文取得 |
| 排序规则 | 创建时间降序，同一时间再按唯一订单 ID 降序 |
| 返回范围 | 每页大小，以及按页码取还是从上一页位置继续取 |

`WHERE → ORDER BY → LIMIT` 可以帮助理解查询的含义，不代表数据库一定按这个物理步骤执行。实际访问路径由优化器决定。

## 2. 页码分页：适合直接跳页的列表

```sql
-- 示例：当前用户为 101，取第二页，每页 20 条
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 20;
```

- `WHERE` 确定查哪些记录。
- `ORDER BY` 确定记录的先后顺序。
- `LIMIT 20` 最多返回 20 条；`OFFSET 20` 跳过前 20 条，偏移量从 0 开始。
- 页码从 1 开始时，`offset = (pageNo - 1) × pageSize`。后端需要检查页码、限制每页大小，并避免偏移量计算溢出。

仅按 `created_at` 排序不够：多笔订单可能在同一时刻创建，彼此顺序不确定。补上唯一的 `id`，使固定数据集合下的排序明确。但连续两次请求之间若插入、删除了记录，页码位置仍可能移动。

## 3. 深分页：返回少不等于处理少

```sql
-- 第 1 页
LIMIT 20 OFFSET 0

-- 第 10000 页
LIMIT 20 OFFSET 199980
```

第二种写法通常需要沿查询路径经过大量记录，再跳过前面的结果。即使能借助索引排序，也不能因此认定数据库能直接定位“第 10000 页”。如果还需要大范围过滤、排序或回表，工作量可能进一步增加。

这不是“所有 OFFSET 查询都必须重写”：数据量小、查询频率低、后台需要任意跳页时，它通常更易实现。先看真实耗时、扫描量和使用场景，再决定是否优化。不能把“返回 20 条”当作“只扫描 20 条”，也不能把“用了索引”当作“没有深分页代价”。

## 4. 游标分页：从上一页的最后一条继续

保持排序规则 `created_at DESC, id DESC`。假设上一页最后一条记录是：

```text
created_at = 2026-10-31 10:00:00
id         = 9002
```

排在它后面的记录，必须满足“时间更早”，或者“时间相同但 ID 更小”：

```sql
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 101
  AND (
    created_at < '2026-10-31 10:00:00'
    OR (
      created_at = '2026-10-31 10:00:00'
      AND id < 9002
    )
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这里假设 `id` 是唯一主键，`created_at` 非空，分页过程中排序字段不被修改。实际程序使用绑定参数，保留数据库时间的精度；不要把带小数秒的时间截成整秒后当作游标。

| 游标条件 | 会发生什么 |
| --- | --- |
| 只使用 `created_at < 上次时间` | 会漏掉同一时刻、排在书签后面的订单 |
| 只使用 `created_at <= 上次时间` | 可能把上一页同一时刻的订单再次返回 |
| 时间与 ID 组合比较 | 能准确表达这组排序字段下的后续范围 |

第一页没有游标，省略上述游标条件即可。若改成升序，比较方向也要相应改变；不能只改 `ORDER BY` 而保留原来的小于号。

## 5. 索引需要与查询形态配合

对于本例，可评估按 `(user_id, created_at, id)` 组织的索引访问路径：先定位用户，再沿时间和 ID 的顺序访问后续范围。这里表达的是索引字段的配合关系，不是要求立刻新增一份同名索引。InnoDB 二级索引本就携带主键，具体定义、是否已有等价索引、能否避免额外排序，需要结合现有结构和执行计划确认。

如果增加 `status` 筛选，不能机械照抄索引：固定用户和状态的列表，与固定用户但横跨全部状态的时间列表，可能需要不同的访问路径。参见 [[04-B加树与索引查询路径]]。

多字段比较也能写成元组形式，但写得短不等于优化器利用索引更完整。本篇展开成 `OR` 条件便于理解；真实项目仍应比较执行计划、正确性与实际性能，不承诺某种写法在所有版本下最快。

## 6. 前后端如何传递游标

后端可以返回如下结构，字段命名是当前学习示例：

```json
{
  "items": [
    {"id": 9002, "createdAt": "2026-10-31T10:00:00", "totalAmount": "99.00"}
  ],
  "nextCursor": "由后端编码的书签",
  "hasMore": true
}
```

- 前端展示 `items`，加载下一页时带回 `nextCursor`，不根据订单内容自行推算书签。
- 后端校验游标格式、页大小及排序方式；改变筛选条件或排序时，从第一页重新开始。
- 用户身份与数据权限仍由后端确定。编码或 Base64 不等于授权，不能相信游标中自报的用户或租户身份。
- 需要判断 `hasMore` 时，可查询 `pageSize + 1` 条。若得到 21 条，只返回前 20 条，以**第 20 条、即最后一条实际返回的记录**生成游标；第 21 条仅用于判断还有后续，不能用它生成书签而漏掉这一条。
- 页大小之外，是否返回总数是单独的产品选择。精确计数可能有额外开销，不能因为用了游标就默认得到总页数。

## 7. 选择方式与剩余边界

| 场景 | 倾向方案 | 需要接受的代价 |
| --- | --- | --- |
| 小规模后台列表，需要输入页码跳转 | 页码分页 | 深页可能慢；数据变化会影响页位置 |
| 手机订单列表、持续加载下一页 | 游标分页 | 通常不能直接跳到任意第 N 页 |
| 必须导出一个确定时点的完整结果 | 单独设计导出任务及一致性方案 | 不能只靠分页方式保证同一份快照 |

游标不是数据库快照。翻页期间修改排序字段、改变记录是否符合筛选条件，仍可能造成遗漏或重复；严格导出需要额外的一致性设计。普通订单列表适合尽量选用稳定的排序字段，并接受约定范围内的实时变化。

待实践时，可比较浅页、深页和相同位置的游标查询：先核对结果，再记录计划、扫描规模与耗时。`EXPLAIN ANALYZE` 会执行查询，不直接对真实业务环境随意运行，验证方法见 [[05-慢查询定位与优化验证]]。
