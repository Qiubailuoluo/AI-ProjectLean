# Redis 缓存读写与一致性

所属章节：[[00-第四章-数据存储与访问]]。前置：[[06-查询设计与分页]]、[[01-事务边界与异常回滚]]。

本篇为直接阅读稿，尚未逐项讨论或在本机 Redis 实践。围绕“商品详情怎样加缓存”建立主线；伪代码只说明职责和流程，不是完整生产实现。

## 1. 为什么有了 MySQL 还使用 Redis

假设商品 1001 的名称、封面和介绍被反复读取。每次都查询数据库，会产生重复工作；可以把一份适合展示的数据暂存在 Redis，后续请求优先读取它。

当前案例中，MySQL 保存商品业务记录，Redis 保存可重建的查询副本。Redis 也能承担计数、会话等其他职责，但这些能力与“商品详情缓存”不是一套问题，不能因为都用了 Redis 就混为一谈。

| 信息 | 本例的处理倾向 | 原因 |
| --- | --- | --- |
| 商品名称、描述、封面引用 | 可以评估缓存 | 读取多，通常能接受约定范围内的短暂滞后 |
| 商品展示价格 | 可按业务要求缓存 | 页面展示值不直接成为下单成交依据 |
| 可靠扣库存、生成订单 | 由业务和数据库约束保证 | 读到“还有库存”不等于已经抢到库存 |
| 当前用户是否能访问某条数据 | 由后端权限规则确定 | 不能因为缓存命中就跳过必要权限判断 |

需要先说明可以容忍多旧的数据、缓存失败后怎样处理，再决定是否缓存。并非所有查询都值得增加这一层。

## 2. Key、Value 和 TTL 分别是什么

下面是命令示例，未执行：

```text
SET learn:product:detail:v1:1001 '{"id":1001,"name":"示例商品"}' EX 300
GET learn:product:detail:v1:1001
DEL learn:product:detail:v1:1001
```

- Key 是缓存标识；这里用环境/业务、用途、结构版本和商品 ID 组成，命名是本篇约定。
- Value 是对应的展示数据。可以将序列化后的 JSON 放入 Redis String，不代表 Redis String 只能存一句普通文字。
- TTL 是有效期。`EX 300` 表示写入时设置 300 秒过期，只是示意值，不是通用推荐时长。
- 写值和设置过期可用一次 `SET ... EX ...` 完成。普通 `SET` 覆盖已有值时，若不带保留或重设 TTL 的选项，会丢失原 TTL，不能以为旧有效期一定继续存在。[Redis SET 文档](https://redis.io/docs/latest/commands/set/)

如果结果与租户、语言、用户价格或其他权限范围有关，Key 或缓存分层也要区分这些条件，避免不同用户共用不该共用的结果。不要直接缓存包含内部字段的整份 Entity。

## 3. 读路径：旁路缓存 Cache-Aside

应用自己负责“读缓存、回源、填缓存”：

```text
读取商品详情缓存
  ├─ 命中：按业务规则返回
  └─ 未命中：查询 MySQL
        ├─ 商品不存在：明确返回不存在，可按需要缓存短期空结果
        └─ 商品存在：写入缓存并设置 TTL，再返回
```

缓存未命中是正常情况，可能来自首次访问、过期或淘汰。Redis 连接超时则是故障，两者在监控和处理上必须区分。

填充缓存失败时，业务是否仍能返回已查到的数据，是需要明确的降级策略。不能把一次非关键缓存写入失败，机械地变成“商品不存在”。

## 4. 写路径：先成功提交数据库，再使缓存失效

本例先采用容易理解的策略：更新商品 → MySQL 事务成功提交 → 删除该商品缓存 → 下一次读取按需重建。这是当前学习的起点，不是对所有系统的强制规定。[Cache-Aside 官方说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)

两个顺序错误值得特别注意：

- **先删缓存再改数据库**：删除后、数据库更新完成前，另一个请求可能读出旧值并重新填回缓存。
- **在事务方法最后调用 DEL 就认定是提交后删除**：Spring 的事务可能在方法返回、代理完成提交时才真正提交。代码放在最后一行，不自动等于事务已经提交。

Spring 可以使用事务事件的 `AFTER_COMMIT` 阶段衔接提交后处理；它只是执行时机的机制，不会自动把 Redis 纳入 MySQL 事务，也不提供崩溃后一定重试的保证。[Spring 事务事件说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

删除缓存比直接把新值写回更容易控制某些并发乱序问题：两个更新请求若按相反顺序写缓存，旧数据可能最后覆盖新数据。但删除方案仍有竞态，不能因此称为强一致。

## 5. 为什么仍然可能读到旧值

考虑这一组交错，数据库读请求与缓存填充之间存在时间窗口：

| 时刻 | 读请求 A | 写请求 B |
| --- | --- | --- |
| 1 | 缓存未命中，从数据库读到旧商品信息 | — |
| 2 | 暂停，尚未填缓存 | 更新商品并成功提交 |
| 3 | — | 删除商品缓存 |
| 4 | 将之前读到的旧信息填入缓存 | — |

所以，“数据库提交后删除缓存”降低了一些风险，但不能消除所有并发旧值回填。TTL 能促使缓存之后重建，并不证明整个业务在指定时间内一定读到最新值；回源还可能遇到延迟副本等因素。

需要更强保障时，应按实际要求评估版本校验、更新与重建的协调、可靠变更通知等方案。不要只加一个固定延时和第二次删除，就宣称一致性问题完全解决。对下单金额、可靠库存判断等关键动作，应重新经过相应业务校验与可靠数据路径，不能直接相信页面缓存。

## 6. 数据库已提交，但缓存删除失败怎么办

数据库提交之后，再抛异常并不能把已经提交的业务修改自动撤回。此时要同时处理两件事：缓存修复，以及调用方看到的操作结果。

对于需要可靠失效的场景，可沿用 [[04-失败恢复与可靠任务]] 的思路：在业务数据库事务内同时记录待处理的失效任务，提交后由工作程序删除缓存，失败则重试并监控。删除失效任务应按幂等方式处理；不能无限重试而没人发现失败。

这比“仅在内存里提交后回调一次”更能覆盖进程崩溃后的恢复需求，但增加任务表、重试与运行维护成本。普通低风险缓存可以采用更简单的策略；先说清要求，再选择复杂度。

## 7. 三类常见流量问题

| 问题 | 商品案例 | 可评估的应对方向 |
| --- | --- | --- |
| 缓存穿透 | 不存在的商品 ID 被不断查询，请求总是回源 | 输入约束、短期空结果缓存；必要时评估布隆过滤器及其维护成本 |
| 缓存击穿 | 某个热门商品缓存到期，大量请求同时重建 | 同一 Key 的重建请求合并、预热、受控互斥；避免所有请求同时压向数据库 |
| 缓存雪崩 | 大量 Key 集中过期，或缓存服务不可用 | 过期时间适当打散、限流、隔离与可承受的降级路径 |

这些是常用场景分类，实际故障可能同时发生。空结果应采用独立、可识别的表示，不能把“缓存里没有 Key”和“已确认数据库不存在”混成一种状态；新商品创建后也要考虑空缓存失效。

TTL 长短、随机扰动幅度、是否允许返回旧副本，都由访问频率、业务容忍度和数据库承载能力决定，不存在一套固定数字适合全部项目。

## 8. Redis 故障时不能无限回源

“Redis 挂了就全部查 MySQL”只有在数据库能承受时才成立。业务需要设置超时、限制并发与回源量，并监控数据库压力。可选择返回受控错误、允许的旧数据或缩小功能范围；具体取舍要符合业务要求。

建议分别观察命中率、缓存访问耗时、超时率、数据库回源量、热点 Key 和失效任务积压。命中率高也不说明数据一定新，缓存正常也不代表数据库可以忽略。

## 9. 当前方案与待实践

当前以商品详情为例采用旁路缓存，数据库作为该业务记录的可靠来源，提交后失效缓存，并设置 TTL。尚未实现客户端、事务回调、重建协调或可靠重试。

后续实践可以验证：首次回源与再次命中、过期重建、商品更新后的失效，以及 Redis 超时和删除失败时的表现。并发旧值回填需要有意控制执行时序才能观察，单次请求成功不足以证明一致性。

分布式锁、Redis 持久化和高可用、布隆过滤器实现及变更订阅暂留专题深入；不能把“缓存入门阅读稿已整理”写成这些能力已经掌握。
