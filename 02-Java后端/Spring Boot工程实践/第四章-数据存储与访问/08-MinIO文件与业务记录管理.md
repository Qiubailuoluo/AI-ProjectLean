# MinIO 文件与业务记录管理

所属章节：[[00-第四章-数据存储与访问]]。前置：[[01-存储系统分工与扩展选型]]、[[04-失败恢复与可靠任务]]。

本篇为直接阅读稿，尚未逐项讨论或执行真实上传、下载和删除。围绕商品封面与订单附件理解对象存储和业务记录的分工。字段、状态、接口与流程均为当前学习案例，不是 MinIO 或 Spring Boot 强制要求的设计。

## 1. 文件内容与文件的业务归属分开保存

商品图片、订单凭证等文件，需要同时回答两类问题：文件在哪里，以及谁可以把它用在什么业务上。

| 存放位置 | 本例保存什么 | 不代替什么 |
| --- | --- | --- |
| MinIO | 图片、PDF 等文件内容，以及对象自身的元数据 | 不代替应用判断这个用户是否拥有某个订单 |
| MySQL | 文件 ID、对象位置、上传者、状态，以及商品或订单与文件的关联 | 不能只凭一条记录就认定文件必然上传完整 |

例如商品表可以保存 `cover_file_id`，文件记录保存 `bucket` 和 `object_key`。后端先通过文件记录定位对象，再根据当前用途生成访问方式。不要求把大文件本体放进普通商品表，也不要求每个系统都采用独立文件表；这是有附件归属与生命周期需求时可采用的结构。

## 2. Bucket、Object Key 与 URL

```text
bucket     = project-files
object_key = product/1001/一个不可预测的唯一标识.jpg
```

- Bucket 是存放对象的容器，可以承载相应访问、生命周期等配置。
- Object Key 是对象在 Bucket 内的名称；其中的 `/` 可用作组织前缀，不等同于本机真实文件夹路径。
- 定位对象通常需要 Bucket 和 Key；开启版本管理并需要精确定位历史内容时，还可能涉及版本 ID。
- URL 是某次访问对象的地址或入口。域名、代理和签名可能变化，不能把一个临时签名 URL 当作永久存储位置。

当前约定由后端生成唯一 Key，保留原始文件名作展示信息。不能直接让用户指定任意已有 Key，也不要仅用 `头像.jpg` 这种常见名称定位对象，以免覆盖或错误引用。

```text
文件记录示意
id / bucket / object_key / original_name / size / content_type
uploader_id / status / created_at

商品或订单记录
通过 file_id 与文件记录关联
```

是否允许同一文件被多个业务引用，应先明确规则。允许共享引用时，删除某个关联不意味着可以立即删除底层文件。

## 3. 两种上传路径

| 方式 | 文件经过哪里 | 适合的起点与代价 |
| --- | --- | --- |
| 后端转发上传 | 前端 → Spring Boot → MinIO | 流程集中，容易衔接业务校验；文件流量和资源消耗经过后端 |
| 预签名直传 | 前端先申请许可，再直接向 MinIO 上传 | 可减轻后端传输压力；需要上传会话、完成确认、跨域及生命周期管理 |

后端转发不代表把整个文件一次性读入内存。实际实现要采用适当的流式处理、大小限制和超时，并关闭响应或输入流。文件大小和并发量较高时尤其需要考虑资源占用。

MinIO Java SDK 提供上传、获取对象信息、读取、删除和生成预签名 URL 等能力；实际方法与参数应以项目使用的 SDK 版本为准。[MinIO Java SDK API](https://github.com/minio/minio-java/blob/master/docs/API.md)

## 4. 预签名直传：许可、上传、确认、绑定

下面是一种可供实践的业务流程，状态名只是本例约定：

1. 用户申请上传。后端验证身份、用途和配额，为本次上传生成新的 Key，保存 `PENDING` 文件记录，并返回短期上传许可。
2. 前端按照许可的地址、HTTP 方法及必要请求头上传文件。后端的长期访问密钥不发送给前端。
3. 前端通知后端“上传完成”。这条通知只是声明，不能直接把文件标成可用。
4. 后端根据本次上传记录检查对象是否存在、实际大小及需要核验的完整性信息；必要时读取内容做格式或安全检查。可信校验通过后，将文件标为 `READY`。
5. 创建或修改商品时传入 `fileId`。后端检查当前用户是否有权使用该文件、状态是否就绪、用途是否匹配，再在数据库事务内绑定商品与文件。

`statObject` 可以获取对象信息和元数据，但客户端上报的 Content-Type 或对象元数据本身不证明文件内容真实可信。对明确限定大小、格式、校验值的上传，应选择能落实这些约束的上传机制，并在确认时验证，而不是仅凭签名 URL 存在就认为全部约束已被强制执行。

**确认完成后还要考虑“对象会不会被再次覆盖”。** 预签名上传地址一般不能简单视为一次性票据；以 Amazon S3 为例，有效期内可以多次使用，对同一 Key 上传会替换对应对象内容。[S3 预签名 URL 说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

在具体 MinIO 部署中，应验证所用接口、版本管理和策略的实际行为。可按需求采用暂存 Key 与最终 Key 分离、发布到受保护的最终位置，或绑定经过核验的特定版本等方案；不要仅凭一次检查就保证后续内容永远不变。

## 5. 为什么 MySQL 事务不能包办上传

```text
文件上传成功
    ↓
保存业务关联失败或数据库事务回滚
    ↓
MinIO 中的文件仍可能存在
```

普通数据库事务只管理参与该事务的数据库操作，不会因为加上 `@Transactional` 就自动撤回已完成的 MinIO 上传。文件删除、生成临时地址等外部动作也不自动拥有相同的提交与回滚语义。

对于上传成功但业务未绑定的文件，可记录用途、创建时间和状态，设置合理宽限期后由清理任务处理。清理时重新确认没有引用、没有仍有效的上传或绑定流程，并通过状态转换协调并发，不能只按文件年龄直接删除。

上传或确认请求超时也不等于上传必然失败。重试应复用同一上传会话或能确认结果的标识；确认接口要允许安全重复调用，避免反复产生新的文件和业务关联。

## 6. 下载：业务权限与存储权限分工

对于订单附件，本例默认使用私有访问路径：

```text
前端请求订单附件
    ↓
后端验证登录身份、订单数据权限、文件状态与关联
    ↓
后端转发文件，或签发短期下载 URL
```

商品公开封面与订单私有凭证可以采用不同的访问策略。不能为了显示一张图片，就把所有附件所在的 Bucket 改为公开。

预签名 URL 是临时访问能力，拿到地址的人在其有效条件内可能直接使用它。有效期按用途设置，不把私有签名地址长期保存到业务表、日志或公开笔记。用户被取消权限后，已经发出的地址也未必立刻失效；要求每次实时鉴权的场景，可考虑由后端代理访问或其他适用控制，而不是单纯延长签名时间。

前端能否访问还与实际网络入口有关。后端能连接内部 MinIO 地址，不代表手机或浏览器也能连接；浏览器直传还需要正确的跨域配置。此处只记录原理，部署配置放后续章节，不修改本机环境。

## 7. 换图与删除：先保护有效业务，再回收旧对象

换封面可以按以下思路组织：新文件验证就绪 → 数据库事务内切换商品引用 → 提交后评估回收旧文件。新文件或数据库更新失败时，旧引用仍可继续使用。

删除私有附件时，可以先在数据库中标记不可访问并记录待删除任务，成功提交后再异步删除对象；失败则重试和监控。这与第三章的可靠任务思路相连，不能只执行一次远程删除后就丢弃恢复线索。

| 异常情况 | 需要处理的业务结果 |
| --- | --- |
| 数据库已标记删除，MinIO 删除失败 | 应用拒绝新的业务访问；任务继续回收物理对象 |
| MinIO 已删除，任务完成标记保存失败 | 重试应能识别对象已不存在，安全完成任务 |
| 底层文件还有其他有效引用 | 不立即删除共享对象 |
| 上传未完成或新文件迟迟未绑定 | 宽限期与状态检查后再清理，避免与正常流程竞争 |

版本管理、保留策略或对象锁会影响物理清理，不能将一次普通删除调用直接等同于永久擦除所有历史版本。业务删除状态、临时地址有效期与存储回收是三个需要协调的方面。

## 8. 谁负责什么

| 层或组件 | 本例职责 |
| --- | --- |
| Controller | 接收上传/确认/下载请求，取得当前身份，组织 HTTP 响应 |
| 业务 Service | 决定能否上传、绑定、访问或删除，维护状态与业务关联 |
| 文件存储组件 | 封装 MinIO SDK 操作、对象信息与技术异常，不自行决定订单权限 |
| Mapper | 保存文件元数据、业务引用和可靠任务 |
| 后台任务 | 在受控条件下重试、核对并回收，记录失败和积压 |

这与 [[02-目录结构与基础设施]] 的分工一致：技术组件提供能力，业务决定怎样使用。不要让 Controller 同时承担文件流转、订单授权、数据库事务和失败恢复的全部逻辑。

## 9. 阅读后的实践方向

可从后端转发一个小文件开始，再验证业务绑定与私有下载。需要直传时，再补上传会话、完整性确认及防覆盖策略。重点观察上传成功但数据库失败、重复确认、下载越权、换图失败和删除重试等情况，而不只是“上传后浏览器能显示图片”。

大文件分片、断点续传、恶意内容检测、版本管理、生命周期配置和生产备份留待专题实践。SDK 能上传文件，不等于这些能力已经自动具备。
