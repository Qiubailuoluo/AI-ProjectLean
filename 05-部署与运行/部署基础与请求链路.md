# 部署基础与请求链路

本篇维护跨路线复用的部署基础。Spring Boot 的具体构建与运行见 [[00-第六章-部署与运行]]；Vue、Flutter 等后续按各自构建和运行方式引用，不复制另一套通用概念。

## 从“代码在电脑上”到“用户可以访问”

源码是维护和构建的输入，产物是准备运行或发布的内容，进程是正在执行的程序，服务是向调用方持续提供能力的运行形态。这几件事不能互相等同：上传了文件不等于程序已经运行，进程存在也不代表请求能成功。

| 概念 | 订单系统中的例子 | 常见误解 |
| --- | --- | --- |
| 主机与运行环境 | 运行后端的计算机或容器环境 | 把“服务器”只理解为某个软件 |
| 进程 | 正在运行的 Java 应用 | JAR 文件在磁盘上就说明应用在运行 |
| 监听地址与端口 | 后端在指定地址的 8080 端口接收请求 | 任意设备都能访问服务自己的 localhost |
| 域名与 DNS | 用户通过域名找到预期入口 | 域名已经解析就说明后端应用健康 |
| 反向代理 | Nginx 接收请求后转给后端实例 | 有代理后无需业务认证和数据权限 |
| TLS | HTTPS 连接中的传输保护和服务身份验证 | 使用 HTTPS 就说明接口业务没有漏洞 |

`localhost` 或回环地址指向请求发起者所在的网络环境。用户手机、Nginx 进程和容器中的后端，看见的本地地址可能分别指向不同对象。

## 一条完整访问链路

```text
浏览器或移动应用
    → 域名解析与网络连接
    → TLS / Nginx 等访问入口
    → 后端监听地址和接口路径
    → 认证、校验、业务处理
    → MySQL / Redis / MinIO 等依赖
    → 返回结果
```

实际系统可以没有独立反向代理，也可以包含负载均衡、网关或其他入口。图中是理解用的常见模型，不是每个学习项目必须填满的部署清单。

静态前端资源与 API 后端也有不同职责：浏览器下载页面脚本后，还会按 API 地址发送请求；页面能打开不代表 API 可用。Flutter 应用能够安装也不代表手机能访问后端配置里的内网地址。

## 请求地址必须逐段对应

对外地址、代理转发后的路径、应用上下文路径和 Controller 映射必须配合。若对外是 `/api/orders`，应明确后端实际接收到的是 `/orders` 还是 `/api/orders`，不能凭名称猜测。

Nginx 的 `proxy_pass` 是否包含 URI 会影响路径替换规则；具体示例见 [[03-反向代理与访问路径]]。[Nginx 代理模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

跨域是浏览器对不同源访问的限制，与网络连通、业务权限不是同一问题。客户端能发送请求、服务端愿意执行、浏览器允许页面读取响应，需要分别核实。不要用任意放行跨域来掩盖错配的域名、端口或鉴权机制。

## 运行状态分层确认

由近到远确认程序是否启动、是否监听、应用本地请求是否成功、代理是否能访问上游、外部入口是否能抵达，再核对业务依赖与结果。这样可以缩小问题范围，而不是同时修改端口、代理和数据库参数。

Nginx 读取自己的配置，Spring Boot 读取应用配置；改了一个文件，不等于另一个程序也会改变。配置检查、重新加载与应用重启应遵循各自机制。[Nginx 基础说明](https://nginx.org/en/docs/beginners_guide.html)
