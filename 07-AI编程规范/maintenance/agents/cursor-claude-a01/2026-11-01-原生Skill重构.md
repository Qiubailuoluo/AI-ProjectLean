# 原生 Skill 重构（v0.30 – v0.50）

参与者：cursor-claude-a01。日期：2026-11-01。范围：`07-AI编程规范/` 从 v0.23 到 v0.50。状态：已实施，静态检查通过；真实客户端触发与回归任务**未验证**。

## 起因：对 v0.23 的审查结论

| 发现 | 影响 |
| --- | --- |
| Cursor 中没有自动入口，`SKILL.md` 不会被默认读取 | 规范可能根本没被用上 |
| Skill 正文只列“去读哪些文件”，没有自足的硬规则 | 依赖多跳读取，容易漏读 |
| 目录名与 `name` 不一致，靠 `../../../common/` 跨目录引用 | 不能作为原生 Skill 安装 |
| 文风偏规范文书：多重否定、“按需确定”类无标准的话、长句堆叠 | 模型难以提取成可执行动作 |
| 个别 reference 过于聚合（5KB+，覆盖多个场景） | 只需一部分时也要整份读入 |
| 无办法验证规范是否真起作用 | 版本在涨，效果未知 |

## 决策与依据

**1. 做成原生 Skill，扁平布局，项目级安装**（其中“必须整套安装、同级相对路径”已被决策 10 取代，见 [decisions](../../decisions.md) D-01、D-10）
- 依据：Cursor 原生 Skill 的 `description` 常驻、正文按需加载；要求目录名等于 `name`。
- 用户的使用方式是“压缩包交给别人，AI 读取后在项目里安装”，所以项目级、跨平台（`install.py`，仅标准库）、默认不覆盖同名目录。
- 跨 Skill 引用用同级相对路径 `../<skill>/`，因此必须整套安装。`check.py` 会拦截指向 `skills/` 之外的链接。

**2. 删总路由，顶层 README 只给人看**
- 总路由多一跳，且常驻规则会占上下文。改由 `description` 触发。

**3. 每个 Skill 内置“核心规则”**
- 把最关键的 5–8 条硬约束放进 `SKILL.md`，reference 只作深入材料。写作时对照了已有 reference，发现 Redis 写路径应为“数据库事务提交后再失效缓存”，已按此修正。

**4. 新增 `engineering-baseline`，删除各 Skill 重复的“先读复用与注释”**
- 一个 Skill 承载所有代码任务的底线，省去每个 Skill 多一跳。

**5. 新增技术栈 Skill**：`java-coding`、`typescript-frontend`、`docker-deploy`、`api-contract`、`security-baseline`、`file-upload-download`。
- `file-upload-download` 从 `engineering-baseline` 拆出：上传下载有独立的触发场景，不应让每个代码任务都背着它。

**6. 拆分过大的 reference**
- `资源发布与上传下载`（5.4KB）→ 发布与存储边界 / 上传校验与隔离 / 下载与撤销。
- `文件生命周期`（5.5KB）→ 对象身份与上传确认 / 下载与访问控制 / 替换删除与恢复。
- 依据：“有时只需要一部分”，按场景拆小，由 `SKILL.md` 指路。

**7. 文风重写**：规则见 `扩展指南.md` 的“写作规范”。已重写：18 个 Skill 的导语、按需读取、验证段；`工程底线`、`事务并发与幂等`、上面拆分的 6 份 reference。

**8. Skill 数量**：分析见 `扩展指南.md` 的“Skill 的数量与粒度”。结论：数量不是问题，`description` 重叠才是；细分用 reference，不用新 Skill。

**9. 维护区**：恢复“按 AI 分目录”，个人记录进 `agents/<id>/`；公共的进 CHANGELOG、issues。曾在 v0.30 合并掉的 `agents/`、`shared/` 已从 git 历史恢复。我此前误写进 `90-学习协作记录/重要决策.md` 的条目已撤回，该目录是学习者自己的记录，不放规范维护内容；`学习进度与交接.md` 仅加一句指向 CHANGELOG 的说明。

## 验证与限制

- 已做：`tools/check.py` 静态检查（name 与目录名、description、行数、链接与标题锚点、孤立文件、Skill 内不指向外部）。
- 已做：`install.py --dry-run` 预演。
- **未做**：在真实 Cursor 里安装并确认自动触发；回归任务；新增 6 个 Skill 的规则逐条对照官方资料。
- **未重写**：其余约 18 份 reference 仍是旧文风，见 issues I-05。

## 补记：v0.60 自成一体与再次拆分

**决策 10：Skill 自成一体，跨 Skill 只写名称。**
- 原因：路径互链使单个 Skill 无法单独拷贝，且 reference 链到别的 Skill 的 reference，超过“一层深”；名称引用不依赖目录布局，Skill 内部重命名不会连锁破坏。
- 代价：名称引用靠 AI 自行找到目标，不如链接确定。用 `check.py` 校验“Skill 存在、标题对应到文件”来补偿。
- 写法：读 `skill`「参考标题」；同时使用 `skill`。

**决策 11：优先拆 reference，不增 Skill。** 本轮把 4KB 以上、含多个独立场景的 reference 拆成更小的文件（见 CHANGELOG v0.60），Skill 数量不变，常驻成本不变。

**决策 12：reference 都是叶子。** 同一 Skill 内允许链到兄弟文件（如分页设计 ↔ 索引设计），不再链出。

**仍未验证**：真实 Cursor 里能否按名称引用找到目标；Windows；回归任务；新增 6 个 Skill 对官方资料的核对。
