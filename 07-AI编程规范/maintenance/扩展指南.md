# 扩展指南

怎么新增 Skill、补充规则、修改现有内容，同时保持“上下文小、好维护”。

## 设计预算

| 项 | 上限 | 原因 |
| --- | --- | --- |
| `description` | 一两句，≤ 100 字 | 所有 Skill 的 description 常驻上下文，越多越贵 |
| `SKILL.md` | 目标 ≤ 60 行，硬上限 500 行 | 触发后整份进入上下文 |
| 核心规则 | 5–8 条 | 超过说明该拆分 Skill 或把细节下沉到 reference |
| reference | 单文件目标 ≤ 5KB | 场景匹配才读，但读了就整份进入 |

`python3 tools/check.py` 会报告这些数字，并检查链接和孤立文件。

## 新增一个 Skill

1. **先判断是否需要新建**：触发场景、所需知识都明显独立才新建；局部缺口优先改现有 Skill 的核心规则或加一个 reference。
2. 复制 `skills/_template/` 为 `skills/<name>/`。`<name>` 用小写字母、数字、连字符，必须与 `SKILL.md` 里的 `name` 一致。
3. 写 `description`：说清**做什么**和**何时使用**，包含触发词（技术名、动作词）。
4. 写“核心规则”：只写模型**不一定知道**或**容易做错**的内容；删掉常识。每条动作式、可检查。
5. 细节放进 `references/`，在 `SKILL.md` 的“按需读取”里写明**什么场景才读**。reference 只放一层，不互相嵌套。
6. 需要用到其他 Skill 时，只写名称，不写路径：读 `<skill>`「参考文件标题」，或「同时使用 `<skill>`」。仅在条件成立时才写；不复制别处的规则。`check.py` 会检查名称和标题是否存在。
7. 运行 `python3 tools/check.py`，在 `README.md` 的索引表补一行，在 `CHANGELOG.md` 记一条。
8. 在 `regression-tasks.md` 加一个能触发它的任务。

## 修改现有规则

- 一条规则只保留一个主要位置：通用的放 `engineering-baseline`，技术语义放所属技术 Skill，框架集成放对应 `springboot-*`。
- 改 `description` 要同步想一下：会不会让别的 Skill 误触发，或让本 Skill 漏触发。
- 规则里写“必须”“不得”时，写明成立条件，不把单次问题推广成所有任务的要求。
- 示例（订单、库存等）只讲机制；正文要说明“不代表目标项目的业务”。
- 技术事实涉及版本时，写“以目标版本文档为准”，并附官方文档链接，不写“当前最新”之类会过期的话。

## 写作规范

目标：模型读一遍就能照做。规则要短、具体、能检查。

| 做法 | 例子 |
| --- | --- |
| 一条规则只说一件事，一句话说完 | “SQL 参数一律绑定。”，不要把校验、日志、权限塞进同一条 |
| 动词开头，直接说要做什么 | “校验文件的实际格式。” |
| 先写做什么，再用一句话说原因；原因不超过一句 | “用 `compareTo` 比较金额，`equals` 会把 2.0 和 2.00 当成不同值。” |
| 条件写在开头，用“当……时”或小标题 | “直传时：预签名凭据只限目标对象。” |
| 同一概念全篇一个词 | 统一用“授权”“校验”“幂等标识” |
| 长度 | 每条尽量 ≤ 60 字；超过就拆成子项 |
| 判断类内容用列表或表格 | 条件 → 做法，一行一个 |
| 术语第一次出现时给出准确名称 | `rollback-only`、`proxy_pass` 保留原文 |

避免：

- “须……不得……不构成……”这类多重否定堆叠。改成两条正向的话。
- “按项目需要确定”“按风险选择”这类不给标准的话。要么写出判断标准，要么删掉。
- 括号里套括号。拆成子项。
- 为了显得严谨而加的限定词。每个限定词都要对应一个真实的例外。

每份 reference 的结构：**适用范围（一句）→ 规则（分小节）→ 验证清单 → 官方参考**。

## Skill 的数量与粒度

**Skill 多了会有问题吗？** 数量本身不是问题，重叠才是。

| 成本 | 实际影响 |
| --- | --- |
| 常驻的 `description` | 每个约 40–90 字符，27 个合计约 1.5K 字符；到 100 个也不到 6K，可以忽略 |
| 触发后进入上下文的 `SKILL.md` | 每个约 1.5–2.5KB。一个任务触发 4–6 个，合计约 10KB，可以接受 |
| 真正的风险 | 多个 Skill 的 `description` 相互重叠，导致误触发、漏触发，或一次触发很多个 |

所以：

1. **按“一个决策领域一个 Skill”拆**。判断标准：触发场景和需要的知识是否明显独立。
2. **细分用 reference，不用新 Skill**。同一领域里“有时只需要一部分”，就把 reference 按场景拆成小文件（如 MinIO 拆成三份），由 `SKILL.md` 的“按需读取”指路。
3. **`description` 要互斥**。新增前，对照已有 Skill，确认触发词不会大面积重叠；重叠的部分写进其中一个，另一个靠“同时使用某 Skill”引用。
4. **单个 reference 目标 ≤ 4KB**。超过就看能否按场景拆开。
5. **Skill 总数多到难管理时**（比如超过 40 个），先看是否有可以合并的，再考虑按类别加前缀命名（`springboot-`、`vue-`）。

## 技术栈候选（按实际用到再加）

| 候选 | 触发场景 | 说明 |
| --- | --- | --- |
| `flutter-app` | Flutter 页面、状态、网络请求 | 学习地图中已有，尚未建 |
| `maven-gradle` | 依赖管理、多模块构建、版本冲突 | 目前只在 `springboot-project-config` 里点到 |
| `observability` | 日志规范、指标、链路追踪、告警 | 目前只有日志的零散规则 |
| `message-queue` | RabbitMQ / Kafka 的幂等消费、重试、死信 | 事务 Skill 已有幂等原则，缺具体中间件 |
| `ci-cd` | GitHub Actions、流水线、发布门禁 | 与 `docker-deploy` 配合 |
| `test-frontend` | Vitest、组件测试、E2E | 目前 `vue-tooling` 仅覆盖入口 |

## 不要做的事

- 不在 `SKILL.md` 里复制 reference 的内容。
- 不为“看起来完整”新建空壳 Skill。
- 不在规范里写某个具体业务项目的事实；项目事实放项目自己的 `AGENTS.md`。
- 不把维护记录、复盘放进 `skills/`（那里的内容都可能被 AI 读到）。
