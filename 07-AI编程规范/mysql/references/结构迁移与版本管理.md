# MySQL 结构迁移与版本管理

适用：DDL 进入版本库、部署顺序、兼容性或生产表结构变更。沿用项目已采用的迁移工具和发布流程，不引入第二套 schema 管理来源。

## 迁移记录

- 将结构变更作为可审查、可排序、可重复部署管理的版本化迁移，与应用代码关联。记录影响对象、数据回填、预估锁/耗时、验证、失败处置和恢复方案。
- 已在共享环境应用的版本化迁移视为不可变；修正通过后续迁移完成。工具的重复执行语义、校验和、基线和失败恢复依其实际配置确认。
- 检查目标版本的 DDL 原子性、隐式提交、在线算法、元数据锁和复制影响；不假设整个迁移可由普通事务回滚或在线执行。
- 大表变更前评估重建时间、锁、临时磁盘、复制延迟和业务负载；按项目工具选择在线变更或分批回填，并定义中止阈值。

## 发布兼容

- 滚动发布或回退方案采用扩展/收缩阶段时，按序增加兼容结构、部署兼容代码、分批回填并核对、切换读写；确认旧版本不再依赖后移除旧结构。
- 破坏性结构变更与应用发布分阶段执行。旧代码运行期间保留其依赖字段和约束；新增 `NOT NULL`、唯一约束、类型收窄或重命名前处理既有数据。
- 数据库结构回退与应用版本回退是不同操作。制定前向修复方案；备份恢复按[备份与恢复](备份与恢复.md)执行，并评估期间写入。
- CI/CD 校验迁移顺序、目标版本和应用兼容性；紧急手工变更须回写迁移历史，保持唯一可追溯状态。

## 验证

在代表性旧结构和数据副本上演练应用顺序、耗时、锁、失败恢复及新旧代码并行。生产发布前确认备份、监控指标、维护窗口、停止条件和负责人。

官方参考：[InnoDB 在线 DDL](https://dev.mysql.com/doc/refman/en/innodb-online-ddl.html)、[原子 DDL](https://dev.mysql.com/doc/refman/en/atomic-ddl.html)。工具行为以项目选用的迁移工具版本文档为准。
