# Redis 数据结构与键值设计

适用：设计 Redis 缓存范围、数据结构、键名、Value、序列化或过期策略。此文聚焦可重建缓存；会话、分布式锁、队列、事件流和持久化主数据需按其交付与恢复语义单独设计。

## 设计输入

设计依据包括数据权威来源、读写比例、访问与更新粒度、查询/排序需求、集合基数、单值大小、允许陈旧时间、失效方式、Redis 故障行为和容量预算。缓存对象应为可从权威源重建的高频读模型；Redis 支持的数据结构本身不构成复制全量业务数据的理由。

缓存不得作为最终授权结论或支付、库存等权威业务结果的唯一依据。密钥及无关敏感个人信息不应写入缓存。展示值不替代写入时的业务校验。大对象、宽查询结果和低频数据仅在访问收益与内存预算明确时纳入缓存。

## 结构选择

| 访问需求 | 起始选择 | 约束 |
| --- | --- | --- |
| 按 Key 整体读写简单值或序列化投影 | String | 明确序列化格式和版本，限制 Value 大小 |
| 按字段读取或更新小型记录 | Hash | 字段语义稳定；多命令更新整条快照时校验版本一致性 |
| 去重成员、存在性或集合运算 | Set | 不保证顺序；限制成员总数 |
| 按分数或顺序范围读取 | Sorted Set | 定义分数精度、同分数排序和成员上限；评估其内存与处理成本 |
| 嵌套文档或字段路径访问 | JSON（需部署版本/模块支持） | 核对环境支持、序列化和内存成本；无必要时不引入额外模块 |

List 和 Stream 表达序列或事件消费语义，不作为普通缓存结构的默认选择。用于队列或事件时，另行定义确认、重复投递、保留、积压和恢复策略。结构选择依据访问操作和容量约束。

## Key 设计

- 使用稳定、可读且有命名空间的格式，例如 `<app>:<env>:cache:<domain>:v<schema>:<scope>:<id>`；具体前缀和大小写遵循仓库约定。
- Key 包含会改变结果的隔离维度，例如租户、语言或权限范围；避免添加不影响结果的维度。敏感信息不得以明文形式作为 Key。
- 查询结果缓存须对规范化后的筛选、排序、分页及访问范围保持唯一映射。避免把原始超长请求拼成 Key；需要摘要时仍要保留作用域并认识到摘要不具备保密性。
- 结构或序列化不兼容时通过版本段隔离，并定义旧 Key 的过期或清理方式；新旧代码不得以不同结构解释同一 Key。
- 多 Key 原子操作或脚本确需同槽时，按 Redis Cluster 规则设计 Hash Tag。统一 Tag 可能形成热点，应避免无差别使用。
- 控制 Key 数量和单键集合基数；避免每请求生成不可回收 Key、无界集合和生产环境全量 `KEYS` 扫描。

## Value、序列化与 TTL

- Value 保存调用方所需的最小读模型字段。不得直接序列化含懒加载关系、ORM 状态、内部凭据或大量无关列的持久化对象。
- 明确字段类型、空值与缺失值语义、时间单位/时区、兼容版本和序列化器。金额保留精确十进制或最小货币单位语义，不经过二进制浮点近似。
- 选择 String JSON、Hash 或其他格式时，比较整体替换与部分更新、读取模式、网络往返、存储开销和 schema 演进；不得仅为使用原生结构增加重复写路径。
- 缓存项设置符合陈旧容忍度的有限 TTL；热点批量过期可按策略加入随机抖动。空值缓存用较短期限并区分“确定不存在”和 Redis 故障。
- 评估目标实例的最大内存、淘汰策略、复制与持久化配置及租户隔离。TTL 不等同于持久保留；淘汰策略也可能提前移除缓存项。

## 与权威数据的一致性

缓存读写、数据库提交后失效、旧值回填竞态、Outbox/持久化失效任务及故障降级见[缓存读写与一致性](缓存读写与一致性.md)及[缓存失效示例](../examples/缓存失效与恢复.md)。集合或查询结果缓存还需明确实体更新如何使关联 Key 失效；未设计可维护的关联失效时，不缓存难以正确刷新的宽查询结果。

## 验证

验证 Key 隔离与敏感信息处理、数据结构与访问操作的匹配度、Value 上限和集合基数、序列化兼容、TTL、淘汰影响、失效覆盖及热点并发回源。缓存故障、过期和重建路径均须覆盖；命中率不构成正确性、容量或回源压力的验证证据。
