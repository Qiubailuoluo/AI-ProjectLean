# Redis 旁路缓存与一致性

适用范围：数据库提供权威业务数据，Redis 保存可重建读副本的旁路缓存。会话、消息队列、分布式锁及 Redis 持久化主数据应依据各自的交付与恢复语义另行设计。

## 读写路径

- 缓存未命中时从权威数据源读取，并按已定义的 Key、Value 和 TTL 写入缓存。权限判断仍基于可信业务上下文，不由缓存命中结果替代。
- 区分缓存未命中、权威数据确认不存在和 Redis 故障。空值缓存须使用独立表示和适当的短 TTL；Redis 故障不得被转换为“记录不存在”。
- 写路径以数据库事务提交为业务成功边界。数据库提交后执行相关 Key 失效；事务完成前的同步删除无法证明数据库已提交。
- 删除失败、消息丢失、并发回填和多次更新乱序可能造成陈旧数据。数据库提交后删除属于最终一致策略，不构成强一致保证。
- TTL 限制单次缓存项的存活时间，但无法单独保证读取时效；陈旧值回填后重新设置 TTL 可能延长陈旧窗口。
- 失效范围覆盖实体详情、关联查询结果及由该实体影响的派生缓存。查询缓存无法维护可靠关联失效时，应避免缓存该结果或采用可验证的版本化方案。

## 失效可靠性

- 允许短暂陈旧且更新频率、风险较低时，可采用提交后删除及有限 TTL。明确可接受陈旧窗口、删除失败处理和监控信号。
- 失效必须最终执行时，优先复用项目可恢复的已提交变更传播机制，核对丢失、重放与顺序保证。采用事务发件箱时，待处理任务与业务变更须同事务提交，再由后台处理器重试。处理须幂等，并具备积压、失败和重放监控。
- 提交后回调可用于安排执行时机，但本身不提供持久化、跨进程投递或失败重试保证。`@TransactionalEventListener(AFTER_COMMIT)` 也不等同于持久消息。
- 更新提交并删除缓存后，先前启动的读请求仍可能将旧值写回。高一致性要求须评估版本校验、写入协调或绕过缓存读取权威数据；延迟双删不足以证明强一致。
- 缓存失效失败发生在数据库已提交之后，业务状态不得报告为数据库回滚。响应、重试和补偿语义应与已提交事实一致。

## 故障与负载

- Redis 故障时是否回源由数据库容量、请求超时、并发限制及业务可用性目标决定。回源路径须限制并发和等待时间，避免故障期间将全量请求转移至数据库。
- 热点 Key 过期、批量过期和缓存重建可按负载评估单飞/互斥重建、TTL 抖动、预热或受控陈旧读取。采用锁时定义持有者校验、过期和释放语义。
- 负缓存仅用于已确认不存在的记录，TTL 短于可接受的新建可见延迟。权限拒绝、超时和数据源故障不得写成负缓存。

## 验证

验证覆盖首次回源、命中、过期、更新提交后失效、删除失败、旧值回填竞态、重复失效任务和 Redis 不可用。核对最终数据、陈旧窗口、数据库回源压力及恢复队列；命中率不足以证明正确性或容量满足要求。

详细 Key、Value 和数据结构约束见[数据结构与键值设计](数据结构与键值设计.md)。提交后失效和旧值回填的时序示例见[缓存失效与恢复](../examples/缓存失效与恢复.md)。
