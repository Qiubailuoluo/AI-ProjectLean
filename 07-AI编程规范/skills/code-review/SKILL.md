# 代码变更审查

审查现有改动并报告可复现或可解释的风险；本 Skill 默认不修改被审查代码。

## 核心规则

- 默认只读，不修改被审查的代码。
- 每个发现必须带文件行号、触发条件和影响；没有证据不报。
- 区分已确认缺陷、条件性风险和风格偏好；风格偏好不算缺陷。
- 按严重级别排序，同一根因合并成一条。
- 未发现问题时明说“未发现可确认缺陷”，并列出审查范围与未验证部分。
- 静态审查结论不等同于测试通过。

## 审查流程

1. 确认审查范围、目标行为和适用项目约定；区分已暂存、工作区、指定提交及分支差异。分支审查核对目标基线与共同祖先，未跟踪文件仅在任务范围内纳入；先看差异，再检查相关调用方、上下文和测试，不把已有无关改动归因于本次提交。
2. 按变更涉及的技术栈使用对应 Skill（如 `springboot-*`、`vue-*`、`mysql-engineering`、`security-baseline`）及其参考，不加载无关领域资料。
3. 检查正确性、安全、并发与事务、数据一致性、性能、错误处理和回归风险。关注输入边界、权限与租户隔离、SQL/命令注入、空值和失败路径、重试副作用、资源边界及查询访问模式。
4. 沿受影响的数据流和调用方验证触发条件；必要时查看相关历史及现有测试，避免仅凭模式匹配下结论。测试缺失只在存在具体未覆盖风险时报告，不自动提高严重级别。
5. 区分已确认缺陷、条件性风险和风格偏好。报告项须包含代码证据、触发条件和实际影响；个人偏好不作为缺陷。
6. 按严重程度排序。每项写明文件与行号、触发场景、影响和最小修复方向；同根因问题合并，避免重复报告。
7. 未发现问题时明确说明“未发现可确认缺陷”，并列出审查范围或无法验证的部分。

严重级别按影响定：严重表示可直接造成重大数据损失或关键安全边界失守；高表示主要功能普遍失效或高风险暴露；中表示在明确条件下导致功能错误、数据不一致或显著资源浪费；低表示影响有限且有可执行修复建议。缺少证据时降低确定性，不抬高级别。

## 输出

```text
## 发现
- [严重级别] path/to/file:line — 问题、触发条件、影响及修复方向

## 已检查
- 覆盖的差异、关键路径及已有测试/CI 证据

## 未验证
- 未运行的检查、缺少的环境或无法从代码确认的假设
```

依据会话授权和仓库约定执行只读检查及必要的本地验证；涉及外部环境或数据写入时核对相应授权。将静态审查结论与构建、测试或运行证据分开报告。共用约束见 `engineering-baseline`「工程底线」。
