# 项目目录与部署边界

先核对现有的构建和运行契约：启动工作目录、`-f`、`--env-file`、构建 context、挂载源。不为目录整洁直接搬移文件。

## 核心规则

- 前后端实现和依赖留在各自目录；Compose、部署脚本、代理配置可集中到 `deploy/`，名称沿用项目约定。
- `.env` 的位置由实际读取它的工具决定。区分 Compose 插值、容器环境、前端构建变量和后端配置。
- 模板只放无敏感值的示例；真实凭据不进版本库和交付产物。
- 构建 context 决定 `COPY` 能访问的文件；`.gitignore` 代替不了 `.dockerignore`。
- 移动 Compose 文件会改变默认项目名和卷名。核对已有数据卷，不把空卷当数据丢失，不自动删卷。
- 日志、数据库目录、备份、用户上传不放进部署目录；AI 记录和临时资料不进前端静态目录。
- 云端交付用明确清单，不同步整个工作区。

## 按需读取

- 目录归属、环境文件、交付清单：[项目目录与文件归属](references/项目目录与文件归属.md)
- 搬移 Compose/环境文件、构建 context、前端 envDir：[部署路径与配置契约](references/部署路径与配置契约.md)
- 编写 Dockerfile、健康检查、资源限制：同时使用 `docker-deploy`
- 本机启动适配、个人环境文件的提交隔离：同时使用 `git-delivery`
- 上传、下载包的发布边界：同时使用 `file-upload-download`

## 验证

在预期的工作目录核对配置实际解析值、构建范围和挂载结果。配置展开可能暴露密钥，不保存完整输出。静态检查不能证明部署成功。
