# 项目目录与文件归属

适用：前后端分仓或同仓组织、根目录整理、环境文件位置、交付清单。按现有的构建和运行契约组织，不为目录整洁直接搬移文件。Compose、构建 context、路径契约见[部署路径与配置契约](部署路径与配置契约.md)。

## 文件归属

- 前后端的实现、依赖、模块配置，留在各自目录。
- 项目说明、接口、AI 记录，归入已有的 `docs/`。
- Compose、部署脚本、代理配置、部署环境模板，可以集中到 `deploy/`，名称沿用项目约定。
- 根目录只保留确有跨项目作用，或工具位置有约束的入口：README、Git 忽略规则、工作区清单、聚合构建配置、CI 入口。
- 服务的 Dockerfile 可以随服务维护，也可以放在部署目录。不强制所有 Docker 相关文件归同一目录。

## 环境文件

- `.env` 的位置取决于实际读取它的工具，不由扩展名决定。
- 区分：Compose 插值、容器运行环境、前端构建变量、后端运行配置。名字相同，不代表内容或安全级别相同。
- 模板只放无敏感值的示例。实际凭据通过受控环境注入，并排除出版本库和交付产物。

## 不该放进部署目录的

- 运行日志、数据库目录、备份、用户上传、下载包。这些属于受控的持久存储。
- 临时外部资料和 AI 记录，也不进入前端静态目录。相关交付边界，使用 `file-upload-download`，读「发布与存储边界」。

## 本地适配

本机启动适配、个人环境文件、已跟踪配置的提交隔离，使用 `git-delivery`，读「本地运行配置」。

## 交付清单

- 上传云端时，使用明确的交付清单：前端发布目录、镜像或后端产物、必要的部署配置。
- 不默认同步整个源码工作区、临时资料、AI 记录、本地凭据。
- 源代码型托管，按平台的构建契约处理，并限制无关的构建内容。
