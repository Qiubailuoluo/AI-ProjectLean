# 项目目录与部署边界

适用范围：前后端分仓/同仓组织、根目录整理、Docker/Compose、环境文件、部署脚本及交付清单。按现有构建和运行契约组织，不为目录整洁直接搬移文件。

## 文件归属

- 前后端实现、依赖及模块配置保留在各自目录；项目说明、接口及 AI 记录归入既有 `docs/`；Compose、部署脚本、代理配置及部署环境模板可集中到 `deploy/`，名称沿用项目约定。
- 根目录保留确有跨项目作用或工具位置约束的入口，例如 README、Git 忽略规则、工作区清单、聚合构建配置和 CI 入口。服务 Dockerfile 可随服务维护，也可放在部署目录；无需强制所有 Docker 相关文件归同一目录。
- `.env` 的位置取决于实际读取工具，不由扩展名决定。区分 Compose 插值、容器运行环境、前端构建变量及后端运行配置；共享名称不意味着共享内容或安全级别。模板只放无敏感值的示例，实际凭据通过受控环境注入并排除出版本库和交付产物。
- 部署目录不保存运行日志、数据库目录、备份、用户上传和下载包；这些属于受控持久存储。临时外部资料与 AI 记录也不进入前端静态目录；相关交付边界见 `file-upload-download` Skill 的[发布与存储边界](../../file-upload-download/references/发布与存储边界.md)。

本机启动适配、个人环境文件及已跟踪配置的提交隔离，按需读取[本地运行配置与提交隔离](../../git-delivery/references/本地运行配置与提交隔离.md)。

## 路径与配置契约

- 搬移 Compose 或环境文件前核对启动工作目录、`-f`、`--project-directory`、`--env-file`、服务 `env_file`、构建 context 及挂载源。插值文件不等于自动注入容器的环境文件；默认查找与相对路径解析按实际版本验证。
- Dockerfile 的位置不决定 `COPY` 的根目录，构建 context 才决定可访问文件范围。`.dockerignore` 放在相应 context 根，或按工具支持使用 Dockerfile 专用忽略文件；`.gitignore` 不替代它。排除密钥、临时资料、无关记录及大文件，不用 `COPY . .` 把整个工作区无筛选地打入镜像。
- 前端环境文件默认位置与构建器 root、环境目录选项及模式相关。以 Vite 为例，改变 `envDir` 必须同步核对脚本和 CI，不能只移动 `.env`；浏览器构建变量仍不得承载服务端密钥。
- 移动 Compose 文件可能影响默认项目标识及由其派生的网络/卷名称。核对已存在的数据卷、挂载、权限和服务地址，不把启动了空卷误报为数据丢失或迁移完成；不自动删除旧卷或执行清库来修复路径问题。

## 验证与交付

- 明确唯一或有意支持的启动方式，同步 README、脚本、CI 和相对引用；在预期工作目录及构建入口核对配置实际解析值、构建范围和挂载结果。配置展开可能暴露密钥，不直接保存或回传完整敏感输出。
- 按影响验证构建、启动、反向代理、环境生效和持久数据路径；静态配置检查不证明真实部署成功。无目标环境时明确未验证项，不因整理目录自行部署。
- 上传云端使用明确的交付清单：前端发布目录、镜像或后端产物及必要部署配置；不默认同步整个源码工作区、临时资料、AI 记录或本地凭据。源代码型托管按平台构建契约处理并限制无关构建内容。
