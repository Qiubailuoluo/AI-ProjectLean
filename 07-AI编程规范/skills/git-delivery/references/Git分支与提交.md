# Git 分支与提交

适用：功能分支、提交整理、推送、冲突处理。先检查仓库的贡献约定、提交模板、分支保护和实际状态。不从示例推定目标分支或远端名称。

## 分支

- 新功能默认在独立的任务分支上做。已有属于本任务的分支，直接复用。
- 创建前确认基线和已有改动的归属。不从未知或无关的功能分支派生。不要因为每次追问就重复创建分支。
- 仓库明确采用主干开发，或用户指定了当前分支时，遵循其约定。
- 分支名表达任务，沿用仓库和工具要求的前缀。没有既有约定时，可用 `feat/<short-purpose>`、`fix/<short-purpose>`。
- 示例不要求重命名现有分支，也不要求绕过工具指定的命名规则。

## 工作区与暂存

- 提交前，分别核对：已暂存、未暂存、相关的未跟踪文件。
- 保留用户和其他任务的修改。按本任务的路径或片段暂存，不无差别地收录整个工作区。
- 混合改动无法可靠拆分时，先确定归属。不要用清空、覆盖、批量还原来解决。
- 一次提交表达一个可审查的逻辑变化。接口、迁移、调用方确有兼容依赖时，可以一起提交。
- 不把无关的格式化、依赖升级、生成物混进来。锁文件和生成物是否提交，以项目规则为准。
- 为本机启动或调试改过配置、脚本、代码时：使用本 Skill 的[本地运行配置](本地运行配置.md)和[提交隔离与产物边界](提交隔离与产物边界.md)。

## 提交信息

- 项目已有的格式和语言优先。没有要求时，用 Conventional Commits：`<type>(<scope>): <summary>`，scope 可省略。
- 标题准确表达最终行为。避免"修改代码""优化一下"这类无法辨识的描述。
- `feat` 表示新增能力，`fix` 表示缺陷修复。`docs`、`refactor`、`test`、`build`、`ci`、`chore` 等，按实际用途选。
- 不兼容的变化，按约定用 `!` 或 `BREAKING CHANGE:`，并说明迁移影响。不要伪装成普通重构。
- 简单变更只写标题即可。正文只补充：动机、关键取舍、兼容影响、实际验证。
- 验证记录区分：通过、失败、未执行。不为满足模板编造结果。
- 复杂的描述，见[变更描述与验证](变更描述与验证.md)。

```text
fix(upload): 阻止未通过校验的附件被下载
```

## 提交、推送、恢复

- 提交前检查：暂存差异、敏感信息、实际验证结果。按项目规则运行必要的检查。不为提交默认新增检查框架。来源不明的仓库脚本，先核查再执行。
- 提交、推送、创建 PR，按当前任务的授权分别执行。授权"提交"，不等于授权合并、发布或改写共享历史。用户已授权的动作，不重复询问。
- 核对远端、分支映射、操作结果。不要把本地成功报告成推送成功。
- 推送被拒绝时：先识别原因和远端的变化。不自动强推，不盲目循环重试。
- 解决冲突时：保留两侧的业务意图，复核最终差异，重跑受影响的检查。不要靠跳过校验或删除他人改动来消除冲突。
- 变基、修改既有提交、强推、清理或删除分支，依照仓库策略和实际授权。不要为整理当前任务，去改写他人或共享的历史。
- 完成后检查工作区剩余的内容，如实报告。不承诺所有文件都已提交。

参考：[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)、[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。GitHub 流程只在项目采用该协作方式时适用。
