# Git 分支与提交

适用范围：功能分支、提交整理、推送和冲突处理。先检查仓库贡献约定、提交模板、分支保护及实际状态，不从示例推定目标分支或远端名称。

## 分支与工作区

- 新功能默认在独立任务分支实现；已有属于本任务的分支直接复用。创建前确认基线和已有改动归属，不从未知或无关功能分支派生，不因每次追问重复创建分支。目标仓库明确采用主干开发或用户指定当前分支时遵循其约定。
- 分支名表达任务，沿用仓库和工具要求的前缀；无既有约定时可用 `feat/<short-purpose>`、`fix/<short-purpose>`。示例不要求重命名现有分支或绕过工具指定的命名规则。
- 提交前分别核对已暂存、未暂存及相关未跟踪文件。保留用户和其他任务的修改；按本任务路径或片段暂存，不无差别收录整个工作区。混合改动无法可靠拆分时先确定归属，不用清空、覆盖或批量还原解决。
- 一次提交表达一个可审查的逻辑变化；接口、迁移和调用方确有兼容依赖时可共同提交。避免把无关格式化、依赖升级或生成物混入；锁文件和生成物是否提交以项目规则为准。

## 本地适配检查

为本机启动或调试修改过配置、脚本或代码时，读取[本地运行配置与提交隔离](本地运行配置与提交隔离.md)，核对仅本地清单与实际暂存差异。已跟踪文件不受 `.gitignore` 屏蔽，未提交的本地值也可能被构建或上传收录；不能只看忽略文件或提交标题判断交付安全。

## 提交信息

- 项目已有格式及语言优先。无既有要求时采用 Conventional Commits：`<type>(<scope>): <summary>`，scope 可省略；标题准确表达最终行为，避免“修改代码”“优化一下”等不可辨识描述。
- `feat` 表示新增能力，`fix` 表示缺陷修复；`docs`、`refactor`、`test`、`build`、`ci`、`chore` 等类型按实际用途选择。不兼容变化按约定使用 `!` 或 `BREAKING CHANGE:` 并说明迁移影响，不伪装成普通重构。
- 简单变更可只有标题；正文仅补充动机、关键取舍、兼容影响和实际验证。验证记录区分通过、失败及未执行，不为满足模板编造结果；复杂描述见[变更描述与验证](变更描述与验证.md)。

```text
fix(upload): 阻止未通过校验的附件被下载
```

## 提交、推送与恢复

- 检查暂存差异、敏感信息和实际验证结果，按项目规则运行必要检查。不为提交默认新增检查框架；受信任范围不明的仓库脚本先核查再执行。
- 提交、推送及创建 PR 按当前任务授权分别执行；授权“提交”不自动扩大为合并、发布或改写共享历史。用户已授权的动作不重复询问。核对远端、分支映射及操作结果，避免把本地成功报告为推送成功。
- 推送被拒绝时先识别原因和远端变化，不自动强推或盲目循环重试。冲突解决保留两侧业务意图，复核最终差异并重新执行受影响检查；不得通过跳过校验或删除他人改动消除冲突。
- 变基、修改既有提交、强推、清理或删除分支依照仓库策略及实际授权；不得为整理当前任务改写他人或共享历史。完成后检查工作区剩余内容并如实报告，不承诺所有文件均已提交。

参考：[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)、[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。GitHub 流程仅在项目采用对应协作方式时适用。
