# 变更描述与验证

适用：PR/MR、交接说明、较复杂的提交正文。优先遵循仓库模板。篇幅按改动复杂度定，简单变更不填无关章节。

## 写法

- 首句说明具体的问题，和修改后的行为。
- 标题围绕最终差异。不沿用已放弃的方案或对话里的临时目标。
- 正文解释：关键实现及原因、受影响的调用方、必要的取舍。只列文件清单，说明不了行为。从差异就能看出的细节，不逐项复述。

## 验证

- 写明执行的命令或场景、结果、实际边界。
- 未运行的项目和原因，分别列出。
- 构建、Mock、集成测试、真实环境验证，不能相互替代。代码审查的结论，不等于测试通过。

## 契约变化

- 接口、数据结构、配置、部署契约变化时，说明：兼容期、迁移或发布顺序、必要的回退限制。
- 用户可见的 UI 变化，按需附脱敏截图。不附真实令牌、签名地址、私有数据。

## 同步

- 描述要与最终差异和验证结果保持一致。范围变了，就重写标题和正文。
- 简洁说明已知限制。不复述对话过程，不写未实现的承诺。

可选的正文骨架，项目模板优先：

```text
问题与结果：<触发条件、原行为、修改后的行为>
关键变更：<影响判断的实现与取舍>
验证：<已执行及结果；未执行及原因>
兼容与发布：<仅涉及契约、迁移或运行风险时填写>
```
