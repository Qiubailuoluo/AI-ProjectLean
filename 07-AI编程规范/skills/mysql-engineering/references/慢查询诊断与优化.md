# MySQL 慢查询诊断与优化

适用：定位高耗时、高频、高资源消耗的 SQL。优化前确认：目标服务器版本、负载窗口、最终 SQL、绑定参数、数据分布。

## 诊断

- 用慢查询日志、Performance Schema 或 `sys` 汇总：重复 SQL、调用次数、总耗时、平均和分位耗时、扫描行数、返回行数。排序问题时，综合看频率、总成本、单次延迟。
- 慢查询日志的阈值、输出目标、采集期限、轮转、保留、访问权限，按环境配置。日志可能含 SQL 字面值或敏感数据。general log 只在受控的诊断窗口启用。
- ORM 或 XML 生成的 SQL，要核对最终文本、实际参数、动态条件、分页、调用频率。只看方法名和模板，还原不出真实负载。
- 保存优化前的证据：SQL 与参数分布、数据量与分布、执行计划、扫描行数、延迟、并发、CPU 和 I/O、临时表、环境版本。日志和样本要脱敏。

## 优化

- 基于证据提出"一个可验证的假设"，再调整索引或 SQL。不要一次改多个变量，不强制索引，不靠放大服务器参数掩盖根因。
- 优化目标：减少无效扫描、回表、排序、重复调用、传输数据。
- 分页要有稳定的排序。深 OFFSET、N+1 查询、全量读取，按实际访问模式评估。
- 在有代表性的数据和可比的负载下对照：正确性、p50/p95 延迟、吞吐、资源、读写成本、执行计划。小样本、空缓存、单次请求，得不出性能结论。
- 高风险的 SQL、索引、参数变更，先在隔离环境验证。生产观测和变更，遵循项目的授权与发布流程。
