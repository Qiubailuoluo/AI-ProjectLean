# MySQL 索引设计与执行计划

适用：新增、调整或删除索引，或解释单条查询的执行计划。依据目标版本、存储引擎、统计信息和实际查询形态判断。

## 索引设计

- 从实际 SQL 的过滤、连接、排序、分组和返回列设计候选索引；结合选择性、数据分布、查询频率及写入成本。单列索引数量不等于有效覆盖。
- 复合索引按常用条件组合、等值/范围条件和排序顺序设计。左侧前缀通常决定可用范围；范围条件、表达式、隐式类型转换和排序方向可能改变后续列的利用方式，须用目标版本执行计划验证。
- 覆盖索引可减少回表，但增加索引宽度、磁盘和缓存占用，并抬高写入与维护成本；只加入能证明有收益的列。
- 检查主键、唯一键、外键及重复或前缀重叠索引。删除索引前检查线上查询、约束和统计使用，必要时用版本支持的不可见索引能力评估。
- 索引变更属于生产 DDL。评估目标版本、表规模、算法与锁能力、复制延迟、磁盘余量及回退方法；`LOCK=NONE` 等声明不保证全过程无阻塞。

## 执行计划

- 使用真实 SQL、绑定参数和接近生产的数据分布检查 `EXPLAIN`；关注实际访问索引、连接顺序、估算行数、过滤、排序/临时表和分区裁剪，不以单个 `type` 或 `possible_keys` 判断优劣。
- `EXPLAIN ANALYZE` 会实际执行语句并采集迭代器耗时和行数。使用前评估资源与副作用，并限定于安全、受控的数据和负载。
- 估算与观测偏差大时检查统计信息、数据倾斜和参数分布；更新统计信息也要评估计划变化并复测。
- 同时核对结果正确性、延迟分布、扫描行数、并发资源消耗和写入成本。执行计划改善不足以证明端到端性能提升。

## 分页设计

- 分页结果采用确定排序；排序值可能重复时追加唯一字段作为稳定排序键。深 OFFSET 可能扫描并丢弃大量记录，返回行数不能代表实际扫描量。
- 游标分页的继续条件须覆盖全部排序字段、方向和唯一补序字段；分页查询 `pageSize + 1` 判断 `hasMore` 时，下一游标取最后一条实际返回记录，不取探测行。
- 游标不提供数据库快照，也不承担权限校验。明确分页期间新增、删除或排序字段变化时的可见性；严格导出或一致性快照另行设计。
- 需任意跳页时评估页码分页；持续加载或深位置查询评估游标。选择依据包括查询成本、接口语义和数据变化要求。
