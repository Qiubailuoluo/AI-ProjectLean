# MySQL 索引设计与执行计划

适用：新增、调整、删除索引，或解释单条查询的执行计划。依据目标版本、存储引擎、统计信息、实际的查询形态判断。分页见[分页设计](分页设计.md)。

## 索引设计

- 从实际 SQL 的过滤、连接、排序、分组、返回列出发设计候选索引。结合选择性、数据分布、查询频率、写入成本。单列索引多，不等于有效覆盖。
- 复合索引按常用的条件组合、等值与范围条件、排序顺序设计。
- 左侧前缀通常决定可用范围。范围条件、表达式、隐式类型转换、排序方向，都可能改变后续列的利用方式，要用目标版本的执行计划验证。
- 覆盖索引能减少回表，但会增加索引宽度、磁盘和缓存占用，抬高写入和维护成本。只加入能证明有收益的列。
- 检查主键、唯一键、外键，以及重复或前缀重叠的索引。
- 删除索引前，检查线上查询、约束、统计的使用情况。必要时，用版本支持的不可见索引评估。

## 索引变更

索引变更属于生产 DDL。评估：目标版本、表规模、算法与锁能力、复制延迟、磁盘余量、回退方法。`LOCK=NONE` 这类声明，不保证全过程无阻塞。

## 执行计划

- 用真实 SQL、绑定参数、接近生产的数据分布检查 `EXPLAIN`。
- 关注：实际访问的索引、连接顺序、估算行数、过滤、排序和临时表、分区裁剪。不要只凭单个 `type` 或 `possible_keys` 判断优劣。
- `EXPLAIN ANALYZE` 会实际执行语句。使用前评估资源和副作用，限定在安全、受控的数据和负载上。
- 估算与观测偏差大时，检查统计信息、数据倾斜、参数分布。更新统计信息也会改变计划，要复测。
- 同时核对：结果正确性、延迟分布、扫描行数、并发资源消耗、写入成本。执行计划变好，不能证明端到端性能提升。
