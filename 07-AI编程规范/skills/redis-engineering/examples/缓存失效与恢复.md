# 缓存失效：提交时机、失败恢复与并发边界

适用范围：数据库为权威源、Redis 保存可重建详情副本的旁路缓存流程。以下时序为机制示例，未连接数据库或 Redis 执行，不定义目标项目业务或缓存策略。

## 提交后失效的事务时序

```text
数据库事务：更新商品 → 成功提交
提交之后：删除对应缓存
下次读取：缓存未命中 → 查询数据库 → 填入缓存并设置 TTL
```

事务方法中最后一行调用 `DEL` 仍可能早于事务提交。
提交前失效存在竞态：并发读请求可能在提交前读取旧值并重新填入缓存。
`@TransactionalEventListener(AFTER_COMMIT)` 可在提交后触发处理，但不提供持久化、跨进程投递或异步执行保证。
无事务时监听器默认不执行，除非启用相应回退配置。

## 可靠失效的持久化任务

```text
同一数据库事务：更新商品 + 保存待失效任务（包含目标缓存标识）
事务提交后：工作程序读取任务 → DEL 缓存 → 记录任务完成
删除失败：保留任务 → 按策略退避重试 → 监控积压与最终失败
```

待处理任务与业务更新须在同一数据库事务中提交，以覆盖数据库提交后进程退出导致的失效丢失。
仅在内存回调失败后补记任务仍存在进程退出窗口。
删除成功但任务尚未标记完成时进程可能退出，因此失效任务应支持幂等重放。
数据库事务提交后，缓存删除失败或抛出异常不会撤销已提交的业务更新。
响应和重试语义应反映数据库提交状态。
低风险缓存可采用较简单的失效方案，但须定义可容忍陈旧窗口和修复路径。

## 可靠删除仍不消除旧值回填

| 顺序 | 读请求 A | 写请求 B |
| --- | --- | --- |
| 1 | 未命中，已从数据库读取旧值 | — |
| 2 | 暂停填缓存 | 更新并提交，删除缓存 |
| 3 | 将手里的旧值填回缓存 | — |

缓存删除成功后仍可能发生旧值回填。严格一致性要求应评估版本校验或重建协调机制。
TTL 支持后续缓存重建；固定延时双删不构成强一致或严格陈旧上限的证明。
权威业务判断仍须经过目标项目的业务规则和可靠数据路径，不以缓存展示值代替。

验证应分别覆盖删除失败后的重试时序和旧值回填时序；单次成功请求不覆盖上述并发场景。
