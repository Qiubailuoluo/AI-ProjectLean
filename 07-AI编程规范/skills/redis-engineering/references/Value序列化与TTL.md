# Value、序列化与 TTL

适用：设计缓存的 Value 内容、序列化格式、过期策略、内存容量。

## Value 放什么

- 只放调用方需要的最小读模型字段。
- 不要直接序列化持久化对象：含懒加载关系、ORM 状态、内部凭据、大量无关列的对象都不行。
- 写清楚：字段类型、空值与缺失值的含义、时间单位和时区、兼容版本、序列化器。
- 金额用精确十进制，或最小货币单位的整数。不经过二进制浮点。

## 选格式

选 String JSON、Hash 还是别的格式，比较这几项：整体替换还是部分更新、读取模式、网络往返、存储开销、schema 演进。不要只为了用原生结构，多出一条重复的写路径。

## TTL

- 缓存项默认设置有限的 TTL，长度符合陈旧容忍度。
- 热点数据批量过期时，TTL 加随机抖动。
- 采用不可变版本或可靠失效机制、不设 TTL 时，要核对时效、容量、回收、故障重建这几项保证。
- 空值缓存用较短的期限，并区分"确定不存在"和"Redis 故障"。
- TTL 不等于持久保留。淘汰策略也可能提前移除缓存项。

## 容量

评估目标实例的：最大内存、淘汰策略、复制与持久化配置、租户隔离。

## 与权威数据的一致性

- 读写、提交后失效、旧值回填、故障降级见[缓存读写与一致性](缓存读写与一致性.md)；具体时序见[缓存失效与恢复](../examples/缓存失效与恢复.md)。
- 集合或查询结果缓存，要先明确"实体更新时，怎么让关联的 Key 失效"。设计不出可维护的关联失效，就不要缓存难以正确刷新的宽查询结果。

## 验证

覆盖：Value 大小上限、序列化兼容、TTL 与淘汰的影响、失效覆盖、热点并发回源、缓存故障、过期、重建。命中率不能证明正确性、容量或回源压力。
