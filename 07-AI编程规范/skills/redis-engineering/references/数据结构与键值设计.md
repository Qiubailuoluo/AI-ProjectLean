# 数据结构与 Key 设计

适用：设计 Redis 缓存的范围、数据结构、Key 命名。本文只讲可重建缓存。会话、分布式锁、队列、事件流、持久化主数据，各自按交付与恢复语义单独设计。

## 先想清楚这些

设计前先回答：

- 权威数据在哪里？读写比例、访问和更新的粒度是什么？
- 要不要查询、排序？集合有多大？单个值有多大？
- 能容忍多久的陈旧？怎么失效？Redis 故障时怎么办？容量预算多少？

缓存里放的，应该是"能从权威源重建的高频读模型"。Redis 支持某种数据结构，不是复制全量业务数据的理由。

## 不能放进缓存的

- 最终的授权结论，或支付、库存等权威业务结果：缓存不能作为它们唯一的依据。
- 密钥，以及无关的敏感个人信息。
- 展示值不能代替写入时的业务校验。
- 大对象、宽查询结果、低频数据：只有访问收益和内存预算都明确时才缓存。

## 选哪种结构

| 访问需求 | 起始选择 | 约束 |
| --- | --- | --- |
| 按 Key 整体读写简单值或序列化投影 | String | 明确序列化格式和版本，限制 Value 大小 |
| 按字段读取或更新小型记录 | Hash | 字段语义稳定；多命令更新整条快照时，校验版本一致 |
| 去重、判断存在、集合运算 | Set | 不保证顺序；限制成员总数 |
| 按分数或顺序范围读取 | Sorted Set | 定义分数精度、同分数排序、成员上限；评估内存和处理成本 |
| 嵌套文档或字段路径访问 | JSON（需部署版本或模块支持） | 先核对环境是否支持，评估序列化和内存成本；没必要就不引入额外模块 |

List 和 Stream 表达的是序列或事件消费语义，不作为普通缓存的默认选择。用作队列或事件时，另行定义确认、重复投递、保留、积压、恢复策略。

## Key 怎么设计

- 格式稳定、可读、带命名空间。例如 `<app>:<env>:cache:<domain>:v<schema>:<scope>:<id>`。具体前缀和大小写，遵循仓库约定。
- Key 里要有"会改变结果的隔离维度"，比如租户、语言、权限范围。不要加不影响结果的维度。
- 敏感信息不能以明文放进 Key。
- 查询结果缓存：把筛选、排序、分页、访问范围规范化后，要和 Key 一一对应。不要把原始超长请求直接拼成 Key。用摘要时仍要保留作用域，并记住摘要不保密。
- 结构或序列化不兼容时，用版本段隔离，并定义旧 Key 怎么过期或清理。新旧代码不能用不同的结构解释同一个 Key。
- 需要多 Key 原子操作或脚本且必须同槽时，按 Redis Cluster 规则设计 Hash Tag。统一 Tag 会造成热点，不要无差别使用。
- 控制 Key 数量和单个集合的元素数。避免：每个请求都生成回收不了的 Key、无界集合、生产环境全量 `KEYS` 扫描。

## 验证

覆盖：Key 隔离与敏感信息、结构与访问操作是否匹配、集合元素数上限。Value、TTL 的验证见[Value 序列化与 TTL](Value序列化与TTL.md)。
