# 旁路缓存与一致性

适用：数据库是权威数据源，Redis 保存可重建的读副本（旁路缓存）。会话、消息队列、分布式锁、Redis 持久化主数据，各自另行设计。

## 读写路径

- 缓存未命中时，从权威数据源读，再按已定义的 Key、Value、TTL 写入缓存。权限判断仍用可信的业务上下文，不用缓存命中结果代替。
- 区分三种情况：缓存未命中、权威数据确认不存在、Redis 故障。
  - 空值缓存要有独立的表示，并用较短 TTL。
  - Redis 故障不能当成"记录不存在"。
- 写路径以**数据库事务提交**为业务成功的边界。提交之后再失效相关 Key。事务还没完成就同步删除，不能证明数据库已经提交。
- 陈旧数据可能来自：删除失败、消息丢失、并发回填、多次更新乱序。"提交后删除"是最终一致，不是强一致。
- TTL 只限制单个缓存项的存活时间，不能单独保证读取时效。旧值被回填后重新设置 TTL，反而可能拉长陈旧窗口。
- 失效范围要覆盖：实体详情、关联的查询结果、受该实体影响的派生缓存。查询缓存做不到可靠的关联失效，就别缓存它，或用可验证的版本化方案。

## 失效可靠性

按场景选：

- **允许短暂陈旧、更新不频繁、风险低**：提交后删除，加有限 TTL。要写明：可接受的陈旧窗口、删除失败怎么处理、用什么信号监控。
- **失效必须最终执行**：
  - 优先复用项目里已有的、可恢复的"已提交变更"传播机制，核对丢失、重放、顺序保证。
  - 用事务发件箱（Outbox）时：待处理任务和业务变更在同一个事务里提交，再由后台处理器重试。处理要幂等，并监控积压、失败、重放。

要点：

- 提交后回调可以安排执行时机，但不保证持久化、跨进程投递、失败重试。`@TransactionalEventListener(AFTER_COMMIT)` 也不等于持久消息。
- 更新提交、缓存删除后，之前已经开始的读请求，仍可能把旧值写回。高一致性要求要评估：版本校验、写入协调、或绕过缓存直接读权威数据。延迟双删不足以证明强一致。
- 缓存失效失败发生在数据库**已提交**之后。业务状态不能报告成"数据库回滚"。响应、重试、补偿，都要和"已提交"这个事实一致。

## 故障与负载

- Redis 故障时是否回源，由这些因素决定：数据库容量、请求超时、并发限制、业务可用性目标。回源路径要限制并发和等待时间，避免故障期间把全部请求压到数据库。
- 热点 Key 过期、批量过期、缓存重建，可按负载选择：单飞或互斥重建、TTL 抖动、预热、受控的陈旧读取。用锁时，定义持有者校验、过期、释放的语义。
- 负缓存只用于已确认不存在的记录，TTL 要短于"新建记录可见"的可接受延迟。权限拒绝、超时、数据源故障，都不能写成负缓存。

## 验证

覆盖：首次回源、命中、过期、更新提交后失效、删除失败、旧值回填竞态、重复失效任务、Redis 不可用。核对：最终数据、陈旧窗口、数据库回源压力、恢复队列。命中率不能证明正确性或容量。
