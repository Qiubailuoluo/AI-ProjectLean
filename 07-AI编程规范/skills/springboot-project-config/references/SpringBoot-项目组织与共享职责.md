# Spring Boot 项目组织与共享职责

适用：包结构、MVC 与 DDD 的关系、跨模块共享能力、配置归属。下面是决策约束，不是必建目录清单。

## MVC 与 DDD

- 常见的 Spring Boot 分层按接口、业务、持久化职责组织，目录如 `controller/`、`service/`、`mapper/` 或 `repository/`。这是技术分层，不能直接等同于 MVC。目录名和分层范围服从项目约定。
- MVC 描述表现层的交互；DDD 关注领域模型、业务边界、协作。两者可以组合：用 MVC Controller 接入请求，再按领域边界组织应用、领域、基础设施。
- 简单业务用清晰的分层或业务包即可。领域规则和边界复杂时，再评估 DDD 风格。架构名称本身，不是增加全套目录或抽象的理由。
- 业务包不自动等于构建子模块、领域边界、微服务。目录拆分要对应实际的职责和团队协作边界。

## `common/`

只放"跨模块复用、语义稳定"的能力，例如通用业务异常、错误映射、基础类型。

- 模块专属的错误码、规则、数据结构，归属其业务模块。多个模块调用同一条业务规则，不足以说明它该放进 `common/`。
- `util/`、`constant/`、`base/` 等目录，只在职责明确且确有复用时才建。不预建没有实现的空目录。
- 公共异常和模块异常的边界，使用 `springboot-api`，读「接口与异常」的异常一节。

## `config/`

放 Spring 或基础设施的组装配置，例如 Bean、序列化、跨域、安全过滤器。具体范围取决于项目依赖和配置方式。

- 配置只声明或组装技术能力，不承载业务规则。认证配置不等于业务操作的资源级授权。
- 配置文件、环境变量、密钥管理，沿用项目已有方式。
- 配置职责少时，沿用框架或项目现有布局，不必为了符合示例新建 `config/`。

## 外部集成与其他职责

- 外部服务调用按项目约定放进 `client/`、`integration/`、适配器或基础设施层，并定义超时、失败、数据转换的边界。没有这类集成就不必建目录。
- 自定义校验器、对象转换器，按职责和复用范围归类。接口字段校验、业务规则校验、跨模块共享逻辑，各归各的边界。没有实际需求，不预建 `validation/`、`converter/`。
- 消息、定时任务、批处理入口，按运行方式组织。入口负责接收和适配，业务规则由业务能力承担。
- 领域模型、应用服务、Repository 这些名称，可以用于 DDD 或其他架构风格。已有的 MVC 分层清晰时，不叠加职责重复的同义层。
