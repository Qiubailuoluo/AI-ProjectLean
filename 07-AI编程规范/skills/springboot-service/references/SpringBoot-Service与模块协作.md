# Spring Boot：Service 与模块协作

适用：业务入口、规则编排、权限判断、模块协作。只适用于本次改动涉及的行为。示例不代表目标业务。

## Service 的职责

业务规则、操作权限、流程编排、必要的事务协调。每个业务入口要能说清楚：输入前提、输出、失败条件。

## 输入、校验与安全

- 消息、任务等非 HTTP 入口不经过 HTTP 参数校验。每个入口各自验证可信输入，并在业务边界维护不变量：数量范围、可用状态、合法的状态迁移。
- 身份和权限判断依据调用入口：HTTP 请求用可信认证上下文；任务和消息用可信调用上下文。客户端自报的身份不是认证结果。
- 权威的业务计算由后端规则完成。历史记录按业务语义保存必要的快照，不把客户端提交的最终结果当权威值。

## 模块协作

- 跨模块调用表达明确的业务能力，保留被调用模块的业务规则。`getById` 这类查询方法不隐含状态或权限校验。同进程协作用 Java 调用即可。
- 协作前明确：规则归谁、数据由谁写、失败语义是什么。
- 通过模块公开的业务入口协作。不直接修改其他模块的数据，不依赖其内部实现。
- 跨模块调用本身不会建立独立事务或分布式事务。
- 单一实现用具体的 Service 类。只有存在替换需求或明确的协作边界，才引入接口。
- 新增 Service、helper、组件之前，先查已有实现和复用边界。

## 事务与外部操作

涉及多步写入、并发竞争、重复请求、外部副作用时，使用 `springboot-transactions`。事务注解本身，不能证明所有操作都在事务保护下。

## 异步、定时任务、消息入口

见[异步与非 HTTP 入口](SpringBoot-异步与非HTTP入口.md)。

## 目录组织

MVC 与 DDD 的关系、`common` 的放置边界，使用 `springboot-project-config`。

## 验证

覆盖本次变更涉及的业务前提、权限、失败语义、跨模块影响。涉及事务、并发、外部副作用时，选择能覆盖相应风险的验证。
