# 示例：断言业务事务结束后的持久化结果

适用：需要验证"多项数据库写入共同回滚"的事务场景。下面用代理式声明事务，展示异常传播和回滚断言的机制。代码省略了类型、依赖、测试清理，未编译、未执行；业务名只是示例。其他事务机制，按其实际入口验证。

## 异常捕获会影响事务结果

```java
@Transactional
public void createOrderWithSwallowedFailure() {
    deductStock();
    try {
        saveOrder();
    } catch (RuntimeException e) {
        return; // 吞掉异常：如果事务没被标记 rollback-only，前面的写入可能被提交
    }
}
```

```java
@Transactional
public void createOrderPropagatingFailure() {
    deductStock();
    saveOrder(); // 符合回滚规则的异常会传到事务代理
}
```

- 默认规则下，`RuntimeException` 和 `Error` 触发回滚。受检异常要回滚，需要配置规则。
- 捕获异常后正常返回，不保证事务提交：底层操作可能已把事务标记为 `rollback-only`。
- 验证必须经过 Spring 代理调用。直接 `new` 对象、同类内部调用，验证不了事务注解的代理行为。

## 不同验证方式能证明什么

| 验证方式 | 能证明 | 证明不了 |
| --- | --- | --- |
| Mock 库存 Mapper 和订单 Mapper | 保存失败时异常是否向外传播、分支是否执行 | 真实 SQL、事务回滚、数据库约束 |
| Spring 业务入口 + 真实测试数据库 | 代理、数据库写入、回滚是否按目标配置协作 | 所有生产故障、网络、部署行为 |

- 验证 MySQL 特有的事务行为时，测试数据库的版本和配置要与目标足够一致。
- 只断言异常、HTTP 失败响应、Mapper 调用次数，不足以证明数据已恢复。

## 回滚测试步骤

```text
1. 在独立的测试资源中提交准备数据：库存 5，没有本次请求的订单。
2. 测试调用侧不要预先开启包裹业务入口的事务，经真实代理调用目标方法。
3. 在扣减已执行之后，让订单保存明确抛出预期的异常。
4. 业务入口返回异常后，确认业务事务已经结束。
5. 在新的独立观察事务中查询：库存仍为 5，没有本次请求的有效订单。
```

- 失败点要放在"第一项写入已成功"之后。
- 提交阶段断连会导致结果未知，不适合做基础回滚用例。
- 测试框架在用例结束时做的清理回滚，不是业务回滚的证据。外围测试事务还可能掩盖入口配置问题。
- 真实 HTTP 请求在服务端产生的提交，不会被客户端测试线程的事务清理掉，要单独隔离并清理。
