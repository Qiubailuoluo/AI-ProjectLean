# 示例：按影响行数判定库存更新结果

适用：用条件更新维护数据库数值下限的并发控制场景。下面的 SQL 和代码只说明机制，未编译、未执行；库存、订单名称不代表目标业务。

## 前置条件

- `quantity` 已校验为正整数。负值会让库存增加，零不符合"正数"的业务约束。
- `id` 是商品的唯一标识，表用 InnoDB，字段类型和数量范围能承载本次运算。
- 扣减和订单保存经过 Spring 代理，进入同一个业务事务。
- 其他写库存的入口也遵守同一个不变量。单条条件更新，约束不了别处的无条件写入。

## 条件更新

MyBatis 的参数占位示意，不能直接粘贴到数据库控制台执行：

```sql
UPDATE product
SET stock = stock - #{quantity}
WHERE id = #{productId}
  AND stock >= #{quantity};
```

```java
// 示意：省略类、依赖、异常定义、订单保存。
int rows = productMapper.deductStock(productId, quantity);
if (rows != 1) {
    throw new BusinessException("库存不足或商品不可用");
}
```

- 影响行数为 0：没有记录满足全部条件。原因可能是对象不存在，也可能是库存不足，单看行数区分不了。要区分，可以补充查询，但补充查询不能代替更新条件。
- 按唯一标识更新，影响行数大于 1：当作数据访问异常处理。

## 验证矩阵

| 初始条件与动作 | 应观察的结果 |
| --- | --- |
| 库存 5，买 2，订单保存成功 | 影响 1 行；事务提交后库存 3，有一笔有效订单 |
| 库存 1，两个独立事务同时各买 1 | 正常完成时只有一笔成功，另一笔 0 行失败；最终库存 0 |
| 扣减成功后，订单保存抛出符合回滚规则的异常 | 业务事务结束后，库存恢复原值，没有新增有效订单 |

- 并发验证：用两个独立请求，控制执行时序，在两个事务都结束后核对持久化结果。
- 锁等待、死锁等异常，不能一律映射成"库存不足"。
- "先查询、再无条件扣减"维护不了并发不变量。`@Transactional` 消除不了竞争。
- 条件更新不提供请求幂等。要重试去重，另行定义稳定标识和持久化约束。
