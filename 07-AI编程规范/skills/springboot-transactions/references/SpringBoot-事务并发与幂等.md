# Spring Boot 事务、并发与幂等

适用：数据库原子性、并发控制、重复请求、失败恢复。下面关于代理的说明，以 Spring 默认代理模式为前提。先核实项目的事务管理器、传播方式、回滚配置。

## 事务边界

- 先写清两件事：哪些数据库操作必须一起提交或回滚，事务从哪个入口开始。
- 同一线程、同一事务管理器下，跨包、跨 Service 的调用仍在同一个事务里。跨数据源、跨线程、跨远程服务，不在。
- 默认代理只拦截"经代理进入"的调用：
  - 同一对象内部调用，不会触发新的事务拦截。外层已有的事务仍然覆盖它。
  - 自己 `new` 出来的对象没有代理。
  - 把慢调用拆成 `private` 方法，不会改变事务边界。要调整，就改事务入口或用编程式事务，并定义外部调用失败后怎么恢复。
- 是否回滚，由异常类型、事务属性、事务状态共同决定：
  - 异常被捕获后正常返回，事务可能提交。
  - 已标记 `rollback-only` 的事务，可能到提交时才失败。
  - 只看日志或统一异常处理，不能证明事务的最终结果。

## 并发与业务不变量

- 先写出并发下必须成立的不变量（例如库存不为负），再选机制。事务本身和"先查后改"都不会自动消除竞争。
- 条件更新、行锁、唯一约束，按数据模型和业务语义选。条件更新要覆盖不变量本身：检查入参范围、影响行数、同一事务内的相关记录。
- "先查不存在，再插入"有竞争窗口。用唯一约束或持久化去重时，按具体的约束冲突分类。其他数据库错误，不要当成"重复请求"。
- 事务回滚后要读取竞争结果，就把读取放到能看到最终状态的事务边界里。

## 重试与幂等

- 调用方可能重试、且重复执行会出错时，设计幂等标识并保留结果。谁生成、唯一范围、有效期、怎么查结果，由接口和业务语义定。
- 同一个操作的重试，用同一个标识。新操作用新标识。
- 同一个标识对应了不同的请求内容：返回冲突，不要返回另一个请求的结果。
- 数据库锁失败后到底回滚了多少，不能只看异常名。涉及 MySQL 死锁或锁等待超时的重试时，读[锁失败与重试](../../mysql-engineering/references/测试与验证.md#锁失败与重试)，核实实际事务边界。
- 只靠 Redis 占位、前端禁用按钮、网络重试策略，都不是持久化去重。持久化约束和结果保留时长，按所需保证来定。

## 外部副作用

- 数据库回滚不会撤销：Redis 写入、对象存储操作、通知、其他已提交的事务。
- 超时或响应丢失会让结果不确定。重试或补偿之前，要有确认状态的办法。
- 必须最终完成的外部副作用：把业务记录和待执行任务写进同一个数据库事务，再由后台处理器重试。任务用稳定的事件标识，并允许重复投递。提交后回调、内存事件在进程重启后不保证执行。
- Outbox、分布式锁、独立编排层都是可选的。按一致性目标、故障模型、现有基础设施评估。

## 验证

- 覆盖：中途失败后的最终数据、并发交错、重复标识、同标识不同内容、"提交成功但响应丢失"后的恢复。
- 验证真实 SQL、约束、事务行为，要用匹配的测试资源，并在业务事务结束后查最终数据。
- Mock 出来的影响行数，不是数据库行为的证据。
