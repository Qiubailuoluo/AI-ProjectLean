# 事务回滚：断言业务事务结束后的持久化结果

适用范围：需验证多项数据库写入共同回滚的事务场景。以下 Java 展示异常传播与回滚断言机制，省略类型、依赖和测试清理代码，未编译或执行；业务名称仅为示例。

## 异常捕获与事务结果

```java
@Transactional
public void createOrderWithSwallowedFailure() {
    deductStock();
    try {
        saveOrder();
    } catch (RuntimeException e) {
        return; // 捕获并忽略异常：若事务未标记 rollback-only，之前的写入可能提交
    }
}
```

```java
@Transactional
public void createOrderPropagatingFailure() {
    deductStock();
    saveOrder(); // 符合回滚规则的异常传播至事务代理
}
```

默认规则下 `RuntimeException` 和 `Error` 触发回滚；受检异常需按要求配置规则。
异常捕获后正常返回不保证事务提交；底层操作可能已将事务标记为 `rollback-only`。
验证入口须经 Spring 代理调用。直接 `new` 对象或同类内部调用不能验证事务注解的代理行为。

## 验证能力边界

| 验证方式 | 证明范围 | 未覆盖范围 |
| --- | --- | --- |
| Mock 库存 Mapper、订单 Mapper | 保存失败时异常是否向外传播，分支是否执行 | 真实 SQL、事务回滚和数据库约束 |
| Spring 业务入口 + 真实测试数据库 | 代理、数据库写入与回滚是否按目标配置协作 | 所有生产故障、网络和部署行为 |

验证 MySQL 特有事务行为时，测试数据库版本与配置应与目标足够一致。
仅断言异常、HTTP 失败响应或 Mapper 调用次数不足以证明数据恢复。

## 回滚测试步骤

```text
1. 在独立测试资源中提交准备数据：库存 5，无本次请求的订单。
2. 测试调用侧不预先开启包裹业务入口的事务，经真实代理调用目标方法。
3. 在扣减已经执行后，让订单保存明确抛出预期异常。
4. 业务入口返回异常后，确认业务事务已结束。
5. 在新的独立观察事务中查询：库存仍为 5，无本次请求的有效订单。
```

将失败点置于首项写入成功之后。提交阶段断连可能导致结果未知，不适用于基础回滚用例。测试框架在用例结束时执行的清理回滚不构成业务回滚证据；外围测试事务可能掩盖入口配置问题。真实 HTTP 请求产生的服务端提交不受客户端测试线程事务清理，应单独隔离并清理。
