# 库存条件更新：按影响行数判定更新结果

适用范围：基于条件更新维护数据库数值下限的并发控制场景。以下 SQL 与代码为机制示例，未编译或执行；库存和订单名称不定义目标业务。

## 前置条件

- `quantity` 已校验为正整数；负值会导致库存增加，零值不符合正数业务约束。
- `id` 是商品唯一标识，表使用 InnoDB；字段类型和数量范围能承载本次运算。
- 扣减与订单保存经过 Spring 代理进入同一业务事务。
- 其他库存写入口遵守相同不变量；单条条件更新不约束其他无条件写入路径。

## 条件更新

MyBatis 参数占位示意，不可直接粘贴到数据库控制台执行：

```sql
UPDATE product
SET stock = stock - #{quantity}
WHERE id = #{productId}
  AND stock >= #{quantity};
```

```java
// 示意：省略类、依赖、异常定义与订单保存。
int rows = productMapper.deductStock(productId, quantity);
if (rows != 1) {
    throw new BusinessException("库存不足或商品不可用");
}
```

影响行数为零表示无记录满足全部条件，可能原因包括对象不存在或库存不足。零行数不足以区分具体原因；需区分时可执行补充查询，但该查询不替代更新条件。唯一标识条件下影响行数大于一应作为数据访问异常处理。

## 验证矩阵

| 初始条件与动作 | 应观察的结果 |
| --- | --- |
| 库存 5，购买 2，订单保存成功 | 影响一行；事务提交后库存 3，有一笔有效订单 |
| 库存 1，两个独立事务同时各买 1 | 正常完成时仅一笔成功，另一笔零行失败；最终库存 0 |
| 扣减成功后订单保存抛出符合回滚规则的异常 | 业务事务结束后，库存恢复原值，无新增有效订单 |

并发验证使用两个独立请求并控制执行时序，在两个事务结束后核对持久化结果。锁等待、死锁等异常不得统一映射为库存不足。查询后无条件扣减不维护并发不变量；`@Transactional` 不消除竞争。条件更新不提供请求幂等；重试去重需另行定义稳定标识和持久化约束。
