# Spring Boot 项目组织与共享职责

适用范围：包结构、MVC 与 DDD 组织关系、跨模块共享能力或配置归属变更。以下内容为决策约束，不构成必建目录清单。

## MVC 与 DDD

- 常见 Spring Boot 技术分层按接口、业务和持久化职责组织代码，目录可包括 `controller/`、`service/`、`mapper/` 或 `repository/`。这是分层组织方式，不能直接等同于 MVC；目录名称及分层范围服从项目约定。
- MVC 主要描述表现层交互；DDD 侧重领域模型、业务边界及协作。二者可组合，例如由 MVC Controller 接入请求，再按领域边界组织应用、领域和基础设施职责。
- 简单业务可采用清晰分层或业务包组织。领域规则和边界复杂时，可评估 DDD 风格。架构名称本身不构成增加全套目录或抽象的理由。
- 业务包不自动构成构建子模块、领域边界或微服务。目录拆分应对应实际职责和团队协作边界。

## 应用包中的 `common/`

应用包内的 `common/` 仅承载跨模块复用且语义稳定的能力，例如通用业务异常、错误映射或基础类型。

- 模块专属错误码、规则和数据结构归属其业务模块；多个模块调用同一业务规则，不足以证明该规则属于 `common/`。
- `util/`、`constant/`、`base/` 等目录仅在职责明确且存在实际复用时建立。不得预建无实现职责的空目录。
- 公共异常与模块异常边界见[接口与异常](SpringBoot-接口与异常.md#异常)。

## 应用包中的 `config/`

应用包内的 `config/` 用于 Spring 或基础设施组装配置，例如 Bean、序列化、跨域或安全过滤器；具体范围取决于项目依赖和配置方式。

- 配置声明或组装技术能力，不承载业务规则。认证配置不构成业务操作的资源级授权。
- 配置文件、环境变量和密钥管理沿用项目既有方式。目录或示例不定义项目依赖。
- 配置职责较少时可沿用框架或项目现有布局，无须为符合示例新建 `config/`。

## 外部集成与其他职责

- 外部服务调用可按项目约定放入 `client/`、`integration/`、适配器或基础设施层，并定义超时、失败和数据转换边界。不存在相应集成时无须建立目录。
- 自定义校验器和对象转换器按职责与复用范围归类。接口字段校验、业务规则校验和跨模块共享逻辑分别归属相应边界；无实际需求时不预建 `validation/` 或 `converter/`。
- 消息、定时任务和批处理入口按运行方式组织。入口负责接收与适配，业务规则由相应业务能力承担。
- 领域模型、应用服务和 Repository 等名称可用于 DDD 或其他架构风格；既有 MVC 分层清晰时，不叠加职责重复的同义层。
