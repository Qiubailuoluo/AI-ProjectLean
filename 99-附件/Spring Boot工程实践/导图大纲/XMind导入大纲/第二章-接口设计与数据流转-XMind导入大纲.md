# 第二章：接口设计与数据流转
## 接口表达业务意图
### 创建订单
#### POST /orders 表达购买什么、买多少
#### 后端执行规则并产生明确结果
### 取消订单
#### 可能涉及权限、库存返还和退款
#### 不等于允许任意更新 status 字段
### 失败也是接口契约
#### 输入错误、业务失败、系统故障需区分
#### 不能把所有失败都变成模糊的操作失败
## 谁决定请求中的数据
### 客户端表达意图
#### 提交商品 ID 与购买数量
#### 缺少必要输入由后端再次校验
### 后端取得身份
#### 从可信认证上下文取得当前用户
#### 不相信客户端自报的买家 ID
### 后端确定交易事实
#### 从可信来源取得售价并计算成交金额
#### 初始状态与创建时间按统一业务约定生成
### 查不到可信数据时
#### 商品不存在或无有效售价要明确失败
#### 不改用客户端价格继续成交
### 前后端校验各有用途
#### 前端改善交互，后端保护接口
#### 请求可以绕开页面直接发出
## Controller 与业务输入
### JSON 转换与校验
#### RequestBody 负责请求体转换
#### Valid 配合依赖与字段约束触发校验
### Controller 组织调用
#### 取得身份后调用业务入口
#### 显式组织 HTTP 状态与响应外壳
### 简单场景直接使用 Request
#### 单入口且输入基本一致时可以少一层转换
#### 需接受业务方法对接口结构的依赖
### 需要独立输入时采用 Command
#### HTTP、任务和消息可映射到统一业务输入
#### 不机械建立多份完全重复对象
## 失败处理与错误表达
### 输入错误
#### 数量为零或 JSON 无法转换
#### 在业务调用前形成明确失败
### 业务失败
#### 商品下架、库存不足等预期规则不满足
#### 由业务层表达，接口边界转换响应
### 系统故障
#### 数据库连接或执行发生异常
#### 内部保留上下文和堆栈，对外不泄露细节
### 统一异常处理
#### MVC 内可通过统一处理器组织响应
#### 不负责自动建立事务或保证回滚
### HTTP 状态与业务码
#### 状态表达类别，业务码表达具体原因
#### code 稳定，不依赖中文 message 判断失败
## 身份、权限与状态
### 认证
#### 凭证有效才确认你是谁
#### 安全过滤器通常先于 Controller
### 功能权限
#### 是否具备使用某项功能的资格
#### 需按安全框架配置正确执行
### 数据权限
#### 是否允许取消这一笔具体订单
#### 已登录不代表能操作所有用户数据
### 业务状态
#### 已发货订单未必允许直接取消
#### 权限通过也不能绕过状态限制
### 安全失败处理边界
#### 过滤器认证失败有安全框架自己的处理入口
#### 不能假定都能由 ControllerAdvice 接住
## 创建订单的四条结果链
### 参数非法
#### 转换或校验阶段发现问题
#### 示例为 400 与 INVALID_ARGUMENT，不调用下单 Service
### 商品下架
#### Service 调用商品入口发现不可售
#### 示例为 409 与 PRODUCT_OFF_SHELF，中断后续操作
### 创建成功
#### 可靠扣减与保存完成并确认约定结果
#### 示例为 201 与 SUCCESS，不只是收到请求
### 数据库故障
#### 数据访问或提交阶段异常传播
#### 示例为 500 与 INTERNAL_ERROR，事务按规则处理
### 超时与失败的剩余边界
#### 客户端可能无法确定最终是否成功
#### 结果确认与幂等不能用盲目重试代替
## 阅读与实践边界
### HTTP 映射是当前案例约定
#### 不把示例状态码当作所有项目唯一标准
#### 下载和流式接口可有不同响应形式
### 已讨论、已整理，待实践
#### 安全配置与完整异常处理仍需真实验证
#### 用四种结果串起第一章职责分工
